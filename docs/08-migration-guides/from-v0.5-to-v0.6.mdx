# Migrate Go AI SDK v0.5.x to v0.6.0

v0.6.0 catches up with the TypeScript AI SDK `ai@7.0.153`. Read this page if
you upgrade an application from any v0.5.x release (v0.5.0 to v0.5.3).

Most v0.5.x code compiles unchanged. A few struct fields changed type, and
those fail at compile time. The other changes match TypeScript behavior:
your code still compiles but can behave differently at run time, send
different requests, or return different error text.

How to use this page:

1. Scan the [quick-scan table](#quick-scan-table). Each row gives a pattern
   to search your code for.
2. For each pattern you find, open its section and follow **What to do**.
3. Rows without a match need no action.

Coding agents can follow the [checklist for coding agents](#for-coding-agents)
step by step.

Each entry uses the same template:

- **What changed:** the v0.5 behavior, the v0.6 behavior, and the
  TypeScript reason.
- **Am I affected?** the identifiers, fields, callbacks or wire behavior to
  search for.
- **What to do:** a before/after snippet, or "No action unless you ...".
- **Kind:** `compile error`, `silent behavior change`, `wire/protocol change`
  or `error text only`.

Entries marked "(v0.5.3)" also shipped in v0.5.3. If you are on v0.5.3
already, you can skip them.

## Compile-time changes {#compile-time-changes}

### GenerateObject and StreamObject MaxRetries is a pointer {#object-maxretries-pointer}

- **What changed:** `GenerateObjectOptions.MaxRetries` and
  `StreamObjectOptions.MaxRetries` changed from `int` to `*int`, like
  `GenerateTextOptions.MaxRetries` and TS `maxRetries`. nil uses the default
  of 2 retries. An explicit `0` now disables retries; in v0.5, `0` selected
  the default. A negative value returns `*errors.InvalidArgumentError`.
- **Am I affected?** `MaxRetries:` in a `GenerateObjectOptions` or
  `StreamObjectOptions` literal.
- **What to do:** pass a pointer. Remove `MaxRetries: 0` if you meant the
  default.
- **Kind:** compile error

**Before:**

```go skip-compile
result, err := ai.GenerateObject(ctx, ai.GenerateObjectOptions{
    Model:      model,
    Prompt:     "Generate a recipe",
    Schema:     recipeSchema,
    MaxRetries: 5,
})
```

**After:**

```go skip-compile
retries := 5
result, err := ai.GenerateObject(ctx, ai.GenerateObjectOptions{
    Model:      model,
    Prompt:     "Generate a recipe",
    Schema:     recipeSchema,
    MaxRetries: &retries,
})
```

### Telemetry RecordInputs and RecordOutputs are pointers, and unset records {#telemetry-record-pointers}

- **What changed:** `telemetry.Options.RecordInputs` and `RecordOutputs`
  (also through the deprecated `telemetry.Settings`) changed from `bool` to
  `*bool`. nil means record, as an omitted `recordInputs` / `recordOutputs`
  does in TS. Only an explicit `false` turns recording off.
  `DefaultSettings()`, `WithRecordInputs(bool)` and `WithRecordOutputs(bool)`
  keep their signatures. `ShouldRecordInputs()` / `ShouldRecordOutputs()`
  report the effective value.
- **Am I affected?** `RecordInputs:` or `RecordOutputs:` in a literal (compile
  error), or any hand-built `telemetry.Options{}` / `telemetry.Settings{}`
  that leaves them unset (silent change). **Privacy:** in v0.5 such a literal
  recorded nothing. In v0.6 it records prompts, messages, tool arguments,
  generated text, objects and tool results in your spans.
- **What to do:** wrap values in `telemetry.Bool(...)`. Set both fields to
  `telemetry.Bool(false)` wherever spans must not contain prompts or outputs.
- **Kind:** compile error

**Before:**

```go skip-compile
tel := &telemetry.Options{
    IsEnabled:     telemetry.Bool(true),
    RecordInputs:  false,
    RecordOutputs: true,
}
```

**After:**

```go
tel := &telemetry.Options{
    IsEnabled:     telemetry.Bool(true),
    RecordInputs:  telemetry.Bool(false), // keep prompts out of spans
    RecordOutputs: telemetry.Bool(true),  // or leave unset: nil records
}
```

### Evaluate end-event struct literals use the Decide field names {#evaluate-event-literals}

- **What changed:** `experimental_evaluate` is now `experimental_decide`, as
  in TS. The old type names are deprecated aliases, so their embedded field
  is named after the new type. Reading promoted fields still compiles.
- **Am I affected?** Struct literals of these types, usually in tests:

  | Type | Embedded field to use in a struct literal |
  | --- | --- |
  | `telemetry.EvaluateEndEvent` | `DecideStartEvent` |
  | `telemetry.EvaluationModelCallEndEvent` | `DecisionModelCallStartEvent` |
  | `ai.EvaluateOnEndEvent` | `DecideOnStartEvent` |

- **What to do:** rename the embedded field in the literal, or move to the
  Decide types (see [Deprecated](#deprecated)).
- **Kind:** compile error

```go
end := telemetry.EvaluateEndEvent{DecideStartEvent: telemetry.DecideStartEvent{}}
_ = end
```

### Unkeyed acp.TextContentBlock literals {#acp-text-content-block}

- **What changed:** `acp.TextContentBlock` is now an alias of
  `acp.ContentBlock` (TS #23587), which also carries image blocks (`Data`,
  `MimeType`).
- **Am I affected?** Unkeyed literals such as
  `acp.TextContentBlock{"text", "hello"}`. Keyed literals and
  `[]TextContentBlock` fields keep working.
- **What to do:** use keyed fields.
- **Kind:** compile error

```go
block := acp.TextContentBlock{Type: "text", Text: "hello"}
```

### Some structs are no longer comparable {#non-comparable-structs}

- **What changed:** these structs gained map, slice or function fields (for
  example `Config.Headers map[string]string`), so Go no longer lets you compare them with `==` or use
  them as map keys: `Config` and `Provider` in `assemblyai`, `cartesia`,
  `deepgram`, `elevenlabs`, `fishaudio`, `gladia`, `hume`, `moonshot`,
  `replicate`, `revai` and `stability`; `cerebras.Config`;
  `bytedance.Error`; `klingai.Error`; `openai/responses.OutputTextDeltaEvent`;
  `workflow.WorkflowResult`.
- **Am I affected?** `==`, `!=`, `switch` on, or map keys of these values.
- **What to do:** compare the fields you care about, or use
  `reflect.DeepEqual` in tests.
- **Kind:** compile error

## Core text and streaming {#core-text-and-streaming}

### StreamTextResult.Text() is the final step's text {#streamtext-text-final-step}

- **What changed:** `StreamTextResult.Text()` (and the end event and
  telemetry text) returned the text of every step joined. It is now the
  final step's text, as TS `result.text`. `ReadAll()` still returns every
  step's text. The same applies to harness and external streams.
- **Am I affected?** `.Text()` on a `StreamTextResult` of a multi-step run
  (tools with `StopWhen`).
- **What to do:** use the text that `ReadAll()` returns, or join
  `Steps()` yourself:

  ```go
  all, err := res.ReadAll() // every step's text, as v0.5 Text()
  if err != nil {
  	log.Fatal(err)
  }
  _ = all
  ```

- **Kind:** silent behavior change

### Output is the text when no Output option is set {#output-default-text}

- **What changed:** with no `Output` option, `GenerateTextResult.Output`
  and `StreamTextResult.Output()` were nil. They are now the final step's
  text (a `string`), as TS `output ?? text()`. `GenerateText` sets it for a
  `stop` finish (also `""`), or a finish other than `tool-calls` with text,
  and leaves it nil otherwise. `StreamText` sets it once the run completes,
  whatever the finish reason, and leaves it nil for a failed or aborted
  run. The legacy `ToolLoopAgent` (`Execute`, `GenerateAgent`) and
  `WorkflowAgent.Generate` already returned the text in `AgentResult.Output`
  and `WorkflowResult.Output`, but now follow the `GenerateText` rule: a run
  that ends on a `tool-calls` finish has a nil `Output`. The end event's
  `Output` stays nil without an `Output` option, `WorkflowStreamResult.Output()`
  stays nil without one (TS stream mode parses only an output spec), and so
  does a harness turn's result. JSON-encoded `GenerateTextResult` values now
  carry an `"output"` field.
- **Am I affected?** Code that tests `result.Output == nil` or
  `res.Output() == nil` to detect a call without an `Output` option, or that
  type-switches on `Output` without a `string` case; code that reads
  `AgentResult.Output` / `WorkflowResult.Output` after a run that hit its
  step limit on tool calls.
- **What to do:** no action unless you rely on a nil `Output`. Check whether
  you passed an `Output` option instead, and read `Text` (or `Text()`) for
  the text.
- **Kind:** silent behavior change

### PartialOutput is the step's text when no Output option is set {#partial-output-default-text}

- **What changed:** without an `Output` option,
  `StreamTextResult.PartialOutput()` is now the current step's text so far,
  a `string`. v0.5 returned nil. TS `streamText` parses partial output with
  `output ?? text()` whenever the run keeps its replay buffer, so
  `partialOutputStream` yields the text (review round 70). A
  `StreamTextLowMemory` run without an `Output` still returns nil (TS
  rejects `partialOutputStream` there), and so does
  `WorkflowStreamResult.PartialOutput()` without an output spec (TS
  WorkflowAgent stream mode parses only an output spec).
- **Am I affected?** `PartialOutput()` on a `StreamText` result created
  without `Output:`, especially `!= nil` checks.
- **What to do:** no action unless you use `PartialOutput()` to detect
  structured output. Check your own option instead:

  ```go
  func structuredPartial(opts ai.StreamTextOptions, result *ai.StreamTextResult) any {
  	if opts.Output == nil {
  		return nil // v0.5: PartialOutput() was nil without Output
  	}
  	return result.PartialOutput()
  }
  ```

- **Kind:** silent behavior change

### OnFinishEvent aggregates across steps {#on-finish-aggregates}

- **What changed:** `OnFinishEvent` usage, tool calls and results, sources,
  files and warnings are totals across all steps, and the event adds
  `Content`, `FinalStep` and `ResponseMessages`. v0.5 reported the last
  step.
- **Am I affected?** `OnFinish:` callbacks that read `Usage`, `ToolCalls` or
  `ToolResults` as the last step's values.
- **What to do:** read `event.FinalStep` for the last step only.
- **Kind:** silent behavior change

### Step content tool results keep the raw tool output {#step-content-tool-result-raw-output}

- **What changed:** a `types.ToolResultContent` in `StepResult.Content`,
  `GenerateTextResult.Content`, `StreamTextResult.Content()` and the step and
  end events keeps the tool's raw output in `Result` next to the
  model-facing `Output`. v0.5 cleared `Result` whenever it set `Output`, so
  the raw value of a `ToModelOutput` tool was not in the content at all. TS
  step content `tool-result.output` is the raw output; the model output is
  built only for the response messages (review round 74). Response messages
  and the next prompt are unchanged: their tool results carry `Output` only.
- **Am I affected?** Code that reads `ToolResultContent.Result` from step or
  result content expecting nil, or that marshals step content to JSON (the
  part gains `"result"`).
- **What to do:** no action unless you relied on `Result` being nil. Read
  `Output` for what the model saw and `Result` for the tool's own value.
- **Kind:** silent behavior change

### Usage.TotalTokens is input + output {#total-tokens}

- **What changed:** `Usage.TotalTokens` is input tokens plus output tokens
  for every provider, as TS computes it. v0.5 copied the provider's wire
  `total_tokens`, which some providers compute differently. A model that
  leaves `TotalTokens` unset (a custom `LanguageModel`) gets it filled from
  input + output when either count is set, in `GenerateText`,
  `GenerateObject`, `StreamObject`, `StreamText` and the legacy
  `ToolLoopAgent` loop (TS `asLanguageModelUsage`; review round 74).
- **Am I affected?** Billing or metrics code that reads `.TotalTokens`.
- **What to do:** no action unless you need the provider's own total. Read
  it from the usage's raw provider data.
- **Kind:** silent behavior change

### ReasoningText joins parts with no separator {#reasoning-text}

- **What changed:** `ReasoningText` joins reasoning parts with no separator,
  as TS. v0.5 put a newline between them.
- **Am I affected?** Code that splits `ReasoningText` on newlines or
  compares it with a stored value.
- **What to do:** join the step's reasoning parts with `"\n"` yourself if
  you need the v0.5 text.
- **Kind:** silent behavior change

### StreamText OnError sees error parts only {#streamtext-onerror}

- **What changed:** as in TS, `OnError` is called for the `error` parts of the
  stream: a provider error chunk, a model call that fails to open, a failure
  before the first stream, a later step that fails to prepare or open, an
  incomplete model stream, a tool choice violation, a tool context that fails
  its schema. When the model stream itself fails (`Next` returns an error),
  or a URL-backed generated file download, a tool input callback
  (`OnInputStart`, `OnInputDelta`, `OnInputAvailable`), an approval resolved
  inside the stream or a tool output conversion (`ToModelOutput`) fails, the
  run ends with that error without calling `OnError`. `Err()`, `ReadAll()`,
  `OnStepError` and the telemetry `OnError` still report it. A run whose
  context is cancelled before its first model stream emits `start` and an
  `abort` chunk and calls `OnAbort`, not `OnError`.
- **Am I affected?** `OnError:` in `StreamTextOptions` used as the only place
  that sees fatal stream failures.
- **What to do:** read fatal errors from `Err()` or `OnStepError`:

  ```go
  res, _ := ai.StreamText(ctx, opts)
  if _, err := res.ReadAll(); err != nil {
  	log.Printf("stream failed: %v", err) // also reported to OnStepError
  }
  ```

- **Kind:** silent behavior change

### A StreamText PrepareStep model applies to one step {#streamtext-preparestep-model}

- **What changed:** as in TS (`prepareStepResult?.model ?? model`) and
  `GenerateText`, each step starts from the call's `Model`, and `PrepareStep`
  receives it in `PrepareStepOptions.Model`. In v0.5 a model that
  `PrepareStep` returned stayed in effect for every following step, and later
  `PrepareStep` calls received it as `Model`.
- **Am I affected?** A `StreamText` `PrepareStep` that returns a `Model` only
  on some steps.
- **What to do:** to keep an override for later steps, return it from every
  `PrepareStep` call.
- **Kind:** silent behavior change

### StreamText fires OnLanguageModelCallStart once per attempt {#streamtext-call-start-per-attempt}

- **What changed:** as in TS, each retried attempt to open the model stream
  (`MaxRetries`) is a new model call. `OnLanguageModelCallStart` fires again,
  and the call's `ResponseTimeMs` runs from that attempt. A failed attempt
  gets no `OnLanguageModelCallEnd`.
- **Am I affected?** Code that pairs `OnLanguageModelCallStart` with
  `OnLanguageModelCallEnd`, or counts steps with call starts.
- **What to do:** key on the last start, or count steps with `OnStepStart`,
  which fires once.
- **Kind:** silent behavior change

### StreamText OnChunk sees every error part before OnError {#streamtext-onchunk-error-parts}

- **What changed:** as in TS, `OnChunk` is called for an `error` part before
  `OnError` (review round 69). For an error part of the model's stream it is
  called with the part as the model sent it, before `ExperimentalTransform`
  and the stream retry decision, so `OnChunk` also sees an error part that
  `StreamRetries` retries (it is not in the full stream) and one a transform
  drops; it is not called again for that part. A run that fails before its
  first model stream (an invalid prompt, a model call that fails to open)
  now passes its `start` and `error` parts to `OnChunk`, and a run cancelled
  before its first model stream passes `start`, then calls `OnAbort`, then
  passes `abort`. v0.5 called `OnError` first, never passed a retried error
  part to `OnChunk`, and passed no parts of such runs.
- **Am I affected?** `OnChunk:` callbacks in `StreamTextOptions` that check
  for `provider.ChunkTypeError`, `ChunkTypeStart` or `ChunkTypeAbort`, or
  that rely on `OnError` running first.
- **What to do:** no action unless you do that. Count failures in `OnError`,
  not in `OnChunk`:

  ```go
  func countFailures(opts *ai.StreamTextOptions, n *int) {
  	opts.OnError = func(ctx context.Context, err error) {
  		*n++ // OnChunk also sees retried error parts
  	}
  }
  ```

- **Kind:** silent behavior change

### StreamText OnError runs for the error parts the stream delivers {#streamtext-onerror-transformed-parts}

- **What changed:** with `ExperimentalTransform`, `OnError` now follows the
  error parts that leave the transform chain. An error part a transform
  replaces with a different error reaches `OnChunk` and `OnError` again with
  the new error. An error part that a transform drops from a pre-stream
  failure, a later step's failure or a failed stream retry no longer reaches
  `OnError`. A model stream's own error part still reaches `OnChunk` and
  `OnError` once, before the transforms. TS's event processor calls onChunk
  and onError for every error part except the error value the model stream
  reader already reported (review round 70).
- **Am I affected?** `ExperimentalTransform` functions that rewrite or drop
  `provider.ChunkTypeError` chunks while `OnError:` is set.
- **What to do:** no action unless your transform rewrites or drops error
  parts. To see the run's error whatever the transform does, read `Err()`
  after the stream:

  ```go
  func runError(result *ai.StreamTextResult) error {
  	return result.Err() // not affected by ExperimentalTransform
  }
  ```

- **Kind:** silent behavior change

### A retried StreamText step drops the failed attempt's raw finish reason {#stream-retry-raw-finish-reason}

- **What changed:** when `StreamRetries` retries a step whose failed attempt
  had already sent a finish part, the step's `RawFinishReason` (and
  `StreamTextResult.RawFinishReason()`) comes from the retried attempt only:
  empty if its finish part has none. v0.5 kept the failed attempt's value.
  TS resets the raw finish reason at the retry boundary (review round 69).
- **Am I affected?** Code that reads `RawFinishReason` with `StreamRetries`
  set, for a provider that sends an error after its finish part.
- **What to do:** no action unless you do that. Read the unified reason:

  ```go
  func stepFinish(step types.StepResult) types.FinishReason {
  	return step.FinishReason // RawFinishReason may be empty after a retry
  }
  ```

- **Kind:** silent behavior change

### A stream retry with a transform keeps only the recovered attempt {#stream-retry-transform-content}

- **What changed:** with `ExperimentalTransform` and `StreamRetries`, the
  step recorded after a retried model call now holds only the recovered
  attempt's transformed content: `Text()`, `Steps()`, `Content()`,
  `ResponseMessages()`, the next step's prompt, and `Output()`. v0.5 also
  kept the failed attempt's text and parts, which could break `Output`
  parsing. TS resets the recorded content at the retry boundary (review
  round 70).
- **Am I affected?** `StreamText` calls that set both
  `ExperimentalTransform:` and `StreamRetries:` / `OnErrorRetry:`.
- **What to do:** no action unless you relied on the failed attempt's text
  in the result. It is still in the full stream:

  ```go
  func failedAttemptText(result *ai.StreamTextResult) string {
  	var all strings.Builder
  	s := result.FullStream()
  	for {
  		c, err := s.Next()
  		if err != nil {
  			return all.String()
  		}
  		if c.Type == provider.ChunkTypeText {
  			all.WriteString(c.Text) // includes the failed attempt's deltas
  		}
  	}
  }
  ```

- **Kind:** silent behavior change

### A later StreamText step that fails to start ends the call {#streamtext-continuation-failure-end}

- **What changed:** when a later step of a `StreamText` call fails to
  prepare or open (a `PrepareStep` result that fails validation, a prompt
  that fails conversion, or a model call that returns an error), the stream
  now ends with that step's `error` part and no `finish` part. `OnStepError`
  runs for the step if it started, then `OnEnd` / `OnEndEvent` and the
  telemetry `OnFinish` (onEnd) run with the steps recorded so far.
  `FinishReason()` is `other` and `TotalUsage()` is empty (TS
  `recordedFinishReason ?? 'other'`, `recordedTotalUsage ?? null usage`).
  The telemetry `OnError` is no longer called. `Err()` still returns the
  error. v0.5 failed the call: telemetry `OnError`, no `OnEnd`. Also,
  `OnStepError` now runs before the telemetry `OnStepError` (TS order).
  `WorkflowAgent.Stream` is unchanged (review round 70).
- **Am I affected?** Multi-step `StreamText` calls that rely on `OnEnd` not
  running after a failed later step, on the telemetry `OnError` for it, or
  on `FinishReason()` / `TotalUsage()` after it.
- **What to do:** check `Err()` in `OnEnd`, or after the stream:

  ```go
  func endedWithError(result *ai.StreamTextResult) bool {
  	return result.Err() != nil // v0.5: OnEnd did not run after a failed later step
  }
  ```

- **Kind:** silent behavior change

### A caller cancellation is not a TimeoutError {#caller-cancel-not-timeout}

- **What changed:** with `Timeout.Total` or `Timeout.PerStep` set,
  cancelling the context passed to `GenerateText` or `StreamText` came back

- **Am I affected?** `errors.As(err, &timeoutErr)` used to detect a caller

- **What to do:** check for the cancellation before the timeout:

  ```go
  var te *ai.TimeoutError
  ```

### A cancel during tool-call repair returns the abort reason {#repair-abort-reason}

### The per-step timeout starts before PrepareStep {#step-timeout-before-preparestep}

### A PrepareStep that sets only System changes the step instructions {#preparestep-system-override}

- **What changed:** in `GenerateText` and `StreamText`, a `PrepareStep`

  ```go
  _ = opts
  ```

### ExperimentalStreamTranscribe reports the cancel reason after Close {#stream-transcribe-cancel-reason}

### Rerank `OnEnd` gets its own ranking {#rerank-onend-ranking-copy}

  ```go
  func rerankTop(ctx context.Context, model provider.RerankingModel, docs []string, query string) (*ai.RerankResult, error) {
  ```

## Prompts and validation {#prompts-and-validation}

### Prompt validation matches TS {#prompt-validation}

- **What changed:** `GenerateText`, `StreamText`, `GenerateObject`,
  `StreamObject`, batch text requests and the agent calls return
  `*errors.InvalidPromptError` when neither or both of `Prompt` and
  `Messages` are set, or when `Messages` is an empty non-nil slice, as TS
  `standardizePrompt`. v0.5 sent an empty prompt, or ignored `Prompt` when
  `Messages` was set. `WorkflowAgent` `Generate` / `Stream` (and the
  `WithOptions` forms) return the same `*InvalidPromptError`; v0.5 returned
  plain errors ("workflow: either prompt or messages is required",
  "workflow: use either prompt or messages, not both"). As TS, a
  `WorkflowAgent` call without a prompt or messages is checked after
  `PrepareCall`, so a `PrepareCall` hook may supply the messages.
  System-role messages in `Messages` without `AllowSystemInMessages` (agent
  or call) are rejected there too, with `*InvalidPromptError` ("System
  messages are not allowed in the prompt or messages fields. Use the
  instructions option instead."). `StreamWithOptions` / `Stream` return the
  error directly, before any callback or telemetry. In v0.5, `Generate`
  returned it as `step 1 failed: ...` after `OnStart`, and `Stream` returned
  it from `ReadAll`/`Err`. The checks run in TS order: missing prompt,
  invalid instructions, empty messages, system messages (review round 70).
- **Am I affected?** Calls that set both `Prompt:` and `Messages:`, neither,
  or `Messages: []types.Message{}`; matches on the `workflow: either prompt or
  messages` error text; `types.RoleSystem` messages in
  `WorkflowGenerateOptions.Messages` / `WorkflowStreamOptions.Messages`.
- **What to do:** pass exactly one of them.
- **Kind:** silent behavior change

### GenerateObject and StreamObject reject system messages in Messages {#object-system-messages}

- **What changed:** as TS `allowSystemInMessages` (default false),
  `GenerateObject` and `StreamObject` reject system-role messages in
  `Messages` unless `AllowSystemMessages` (alias `AllowSystemInMessages`) is
  set. `GenerateText` already did. The error is
  `*prompt.UnsupportedSystemMessageError` with the TS text "System messages
  are not allowed in the prompt or messages fields. Use the instructions
  option instead."
- **Am I affected?** `types.RoleSystem` messages in
  `GenerateObjectOptions.Messages` or `StreamObjectOptions.Messages`.
- **What to do:** put the system prompt in `Instructions` (or `System`), or
  set `AllowSystemMessages: true` for trusted messages.
- **Kind:** silent behavior change

### Invalid instructions are an InvalidPromptError {#invalid-instructions}

- **What changed:** as in TS, `InstructionMessages` that are not all system
  messages fail `GenerateText`, `StreamText`, the legacy `ToolLoopAgent` loop
  and batch text requests with `*providererrors.InvalidPromptError`
  ("Invalid prompt: instructions must be a string, SystemModelMessage, or
  array of SystemModelMessage"). In v0.5 the error was an
  `*InvalidArgumentError` ("Invalid argument for parameter instructions:
  ..."). It is now the `Cause`, so `errors.As` on either type matches. The
  checks run in TS order: a missing prompt first, then invalid instructions,
  then empty messages. A `WorkflowAgent` `Instructions` value of an
  unsupported type (not a string, `types.Message`, `[]types.Message` or
  `[]string`) is the same `*InvalidPromptError`, from `NewWorkflowAgent` and
  from the calls; only the effective value is checked (the call's
  `Instructions`, else its `System`, else the agent's), and not one that a
  `PrepareCall` hook replaces, as TS validates `options.instructions ??
  options.system ?? this.instructions` after prepareCall (review round 70);
  v0.5 returned "workflow: unsupported instructions type T".
- **Am I affected?** Code that compares this error's text, including
  `workflow: unsupported instructions type`.
- **What to do:** compare error types, not text:

  ```go
  var promptErr *providererrors.InvalidPromptError
  if errors.As(err, &promptErr) {
  	// invalid prompt or instructions
  }
  ```

- **Kind:** silent behavior change

### Tool calls without results fail the prompt {#missing-tool-results}

- **What changed:** a prompt with assistant tool calls that have no tool
  result fails with `*types.MissingToolResultsError`, as TS
  (provider-executed calls are exempt). A tool result that answers no tool
  call fails with "Tool call `<id>` not found."
- **Am I affected?** Conversation histories you trim or rebuild that can drop
  tool results.
- **What to do:** keep every tool call's result in `Messages`, or remove the
  call too.
- **Kind:** silent behavior change

### The JSON Schema validator enforces more keywords {#json-schema-validator}

- **What changed:** the JSON Schema validator enforces `if` / `then` /
  `else`, `contains`, `dependencies` and `dependentSchemas`. Input that
  passed because they were ignored now fails.
- **Am I affected?** Tool or output schemas that use these keywords.
- **What to do:** fix the schema or the producer of the input.
- **Kind:** silent behavior change

## Tools {#tools}

### Tools in a step run concurrently {#tools-concurrent}

- **What changed:** the tool calls of one step run concurrently by default,
  as TS `Promise.all`, in `GenerateText`, `StreamText`, `ToolLoopAgent`
  (including the legacy `Execute` / `GenerateAgent` loop), approval resumes
  and `WorkflowAgent`. v0.5 ran them one after another. Results stay in call
  order.
- **Am I affected?** Tool `Execute` functions or tool callbacks that share
  state without locking, or that depend on running in order.
- **What to do:** guard shared state with a mutex, or run tools one at a
  time:

  ```go
  one := 1
  opts := ai.GenerateTextOptions{ToolCallConcurrency: &one} // v0.5 behavior
  _ = opts
  ```

- **Kind:** silent behavior change

### An unset ToolChoice reaches the model as auto {#tool-choice-auto}

- **What changed:** as TS `prepareToolChoice`, `GenerateText`, `StreamText`
  and `ExperimentalStartBatch` pass the model `ToolChoice{Type: "auto"}` when
  neither the call nor `PrepareStep` sets one. Requests with tools now carry
  the provider's explicit auto choice (`"tool_choice": "auto"` for OpenAI and
  OpenAI-compatible servers, `{"type": "auto"}` for Anthropic,
  `toolChoice.auto` for Bedrock, mode `AUTO` for Google). The Gateway always
  sends `toolChoice`, and the OpenAI completion and Prodia models warn that
  `toolChoice` is unsupported. Events still report the choice as given. Z.AI
  no longer sends `tool_choice` without tools.
- **Am I affected?** An OpenAI-compatible server that rejects an explicit
  auto choice (for example vLLM started without
  `--enable-auto-tool-choice`), or request matchers that expect no
  `tool_choice`.
- **What to do:** enable auto tool choice on the server, or wrap the model
  with a middleware that restores the v0.5 request:

  ```go
  clearToolChoice := &middleware.LanguageModelMiddleware{
  	TransformParams: func(_ context.Context, _ string, params *provider.GenerateOptions, _ provider.LanguageModel) (*provider.GenerateOptions, error) {
  		p := *params
  		p.ToolChoice = types.ToolChoice{} // send no tool_choice, as v0.5
  		return &p, nil
  	},
  }
  model = middleware.WrapLanguageModel(model, []*middleware.LanguageModelMiddleware{clearToolChoice}, nil, nil)
  ```

- **Kind:** wire/protocol change

### ToolChoice none is enforced {#tool-choice-none}

- **What changed:** a tool call under tool choice `none` now fails
  `GenerateText`, `StreamText` and the agents with
  `*ai.ToolChoiceViolationError` ("Model response contained a tool call even
  though tool choice was none."), as TS. v0.5 ran the tool. Any tool-choice
  violation (none, required or a specific tool) ends the step with finish
  reason `error`.
- **Am I affected?** `ToolChoice: types.ToolChoice{Type: "none"}` with models
  that call tools anyway.
- **What to do:** handle the error:

  ```go
  if ai.IsToolChoiceViolationError(err) {
  	// the model called a tool under tool choice none
  }
  ```

- **Kind:** silent behavior change

### A StreamText tool choice violation ends with finish {#tool-choice-violation-finish}

- **What changed:** the `ToolChoiceViolationError` is an `error` chunk after
  the model output (`OnError` once, as before). The run then ends with a
  `finish` chunk (finish reason `error`), `OnFinish` and `OnEnd`, as TS.
  `Err()` still returns the violation. v0.5 ended the run without `finish`,
  `OnFinish` or `OnEnd`.
- **Am I affected?** Code that treats a missing `OnEnd` as a failure.
- **What to do:** check `Err()` instead.
- **Kind:** silent behavior change

### A provider-executed tool call is never run locally {#provider-executed-not-local}

- **What changed:** in `GenerateText`, `StreamText` and the legacy
  `ToolLoopAgent` loop, a call the provider marks `ProviderExecuted` no
  longer runs a local tool of the same name, as TS runs only calls without
  `providerExecuted`. v0.5 ran the local tool too and added a second result.
- **Am I affected?** A local tool with the same name as a provider tool (web
  search, code execution).
- **What to do:** give the local tool a name the provider's tools do not
  use.
- **Kind:** silent behavior change

### Provider tool results stay in the assistant message {#provider-tool-results-assistant}

- **What changed:** as in TS, every tool result or tool error a provider
  returns now has `ProviderExecuted` set, in `GenerateText`, `StreamText` and
  the legacy `ToolLoopAgent` loop. The step's `Response.Messages` keep it in
  the assistant message next to its call. v0.5 put a result whose provider
  left the flag unset (OpenAI Responses `web_search_call`,
  `image_generation_call` and `program_output`, xAI Responses hosted tools in
  `GenerateText`, a deferred result with no call in the step) in a separate
  `tool` message, which the next turn sent back as a function output. Results
  of your own tools are unchanged.
- **Am I affected?** Code that looks for provider tool results in `RoleTool`
  messages, or reads `ProviderExecuted == false` on them.
- **What to do:** read them from the assistant message:

  ```go
  for _, part := range result.FinalStep.Response.Messages[0].Content {
  	if r, ok := part.(types.ToolResultContent); ok && r.ProviderExecuted {
  		_ = r.Result
  	}
  }
  ```

- **Kind:** silent behavior change

### ToolResults holds no bookkeeping entries {#tool-results-bookkeeping}

- **What changed:** `ToolResults` no longer holds entries for calls awaiting
  approval, auto-denied calls or provider-executed calls without a result.
- **Am I affected?** Code that finds pending approvals or denials in
  `ToolResults`.
- **What to do:** read the approval parts (`ToolApprovalRequestContent`,
  `ToolApprovalResponseContent`) in `Content`.
- **Kind:** silent behavior change

### Provider tool calls are validated against the tool's Parameters {#provider-tool-input-validation}

- **What changed:** `GenerateText`, `StreamText` and the agents validate the
  input of a provider tool call (a tool with `ProviderExecuted: true` or
  `Type: "provider"`) against the tool's `Parameters`, as TS `parseToolCall`
  checks every tool's `inputSchema`. An invalid provider-executed call is
  marked `Invalid` and `Dynamic`; it gets no client tool error, and the
  provider's own result is kept. v0.5 never validated provider tools. Provider
  tools without `Parameters` are not validated. The Parameters of four
  constructors now are the TS input schemas: `xai.MCPServer` and
  `xai.FileSearch` (`{}`; their config, including the MCP authorization
  token, was in `Parameters` as defaults and stays in the tool args),
  `groq.BrowserSearchTool` and the mistral web search tools (no
  `additionalProperties: false`), and the Anthropic regex tool search (no
  `maxLength` on `pattern`) (review round 71). The AI Gateway Browserbase
  search tool enforces TS's `query` length (1-200) and integer `num_results`
  (1-25), Browserbase fetch requires a URI `url`, and the Exa/Perplexity
  union inputs use `anyOf`. The Anthropic code execution tools (2025-08-25,
  2026-01-20) accept `file_text: null` and the Anthropic memory tool accepts
  non-integer `view_range` / `insert_line` numbers, as TS does. The Google
  code execution and OpenAI code interpreter tools now carry their TS input
  schemas (review round 72). The google tools are now `ProviderExecuted` and
  carry TS's input schemas (`{}` objects; code execution `{language, code}`),
  and the OpenAI local shell, shell, apply patch, computer and programmatic
  tool calling tools, file search and image generation (`{}`), and the xai
  web search, X search, code execution, view image, view X video and image
  generation tools now carry their TS input schemas, so their calls are
  validated like other provider tool calls (review round 73).
- **Am I affected?** Provider tools you define yourself with
  `ProviderExecuted: true` or `Type: "provider"` whose `Parameters` do not
  describe the call input; code that reads `Parameters` of `xai.MCPServer(`
  or `xai.FileSearch(` (read `ProviderOptions` for the config);
  `tools.NewBrowserbaseSearch(` and `tools.NewBrowserbaseFetch(` calls with
  out-of-range input; provider-executed `google.CodeExecutionTool()` or
  `openaiTool.CodeInterpreter(` calls whose input lacks `code` / `language`
  or `containerId`; `responses.NewLocalShellTool()`, `NewShellTool(`,
  `NewApplyPatchTool()`, `NewComputerTool()` calls whose input does not match
  TS's shape.
- **What to do:** no action unless your provider tool's `Parameters` are not
  its input schema. Give it the input schema, or none:

  ```go
  var webSearch = types.Tool{
  	Name:             "web_search",
  	Type:             types.ToolTypeProviderDefined,
  	ProviderExecuted: true,
  	// The input the model sends, not the provider's configuration.
  	Parameters: map[string]interface{}{
  		"type":       "object",
  		"properties": map[string]interface{}{"query": map[string]interface{}{"type": "string"}},
  	},
  }
  ```

- **Kind:** silent behavior change

### Tools with an OrderedSchema or a bare JSONSchemaValidator are validated {#tool-input-ordered-schema-validation}

- **What changed:** a tool call is now validated (and its schema defaults
  applied) when the tool's `Parameters` is an `*schema.OrderedSchema` or a
  bare `*schema.JSONSchemaValidator`, as it already was for a map or a
  `*schema.SimpleJSONSchema`. A call that breaks the schema is `Invalid` and
  `Dynamic` with an `InvalidToolInputError`, does not run, and the model gets
  the error (or `RepairToolCall` runs). `ToolCallRepairOptions.InputSchema`
  returns the schema of a bare `JSONSchemaValidator` instead of
  `{"type":"object"}`. TS `parseToolCall` validates every tool's input schema
  (review round 72).
- **Am I affected?** Tools built with `schema.NewOrderedSchema(...)` or
  `schema.NewJSONSchema(...)` as `Parameters` whose model calls do not always
  match that schema.
- **What to do:** no action unless such a tool relied on receiving input its
  schema rejects; loosen the schema or repair the call in `RepairToolCall`.
- **Kind:** silent behavior change

### Provider tool output schemas match TS {#provider-tool-output-schemas}

- **What changed:** the `OutputSchema` of the AI Gateway tools
  (`pkg/providers/gateway/tools`) is now TS's zod JSON schema: nullable fields
  are `anyOf [T, {"type":"null"}]` (v0.5 used `"nullable": true`, which the
  validator ignores, so null fields failed), unions are `anyOf` (was
  `oneOf`), and TS's `required` lists are present. `groq.BrowserSearchTool`
  no longer sets `additionalProperties: false`. `xai.MCPServer`,
  `xai.FileSearch`, the mistral web search tools and the Anthropic regex tool
  search now have TS's output schemas (v0.5 had none). `ai.ValidateUIMessages`
  checks tool outputs against these, as TS `validateUIMessages` does (review
  round 72). Review round 73 adds them for the Anthropic web search, web
  fetch, code execution, BM25 tool search and advisor tools, every google
  tool (`GoogleSearchTool`, `EnterpriseWebSearchTool`, `GoogleMapsTool`,
  `UrlContextTool`, `FileSearchTool`, `CodeExecutionTool`,
  `VertexRagStoreTool`), every OpenAI tool constructor (the custom tool has
  none in TS) and every xai tool, so every built-in provider tool now carries
  TS's output schema.
- **Am I affected?** `ValidateUIMessages` with these tools in `Tools`; code
  that reads `OutputSchema` of these tools (`["oneOf"]`, `"nullable"`,
  `[]string` required lists, which are now `[]interface{}`).
- **What to do:** no action unless you read `OutputSchema`. Read `anyOf` and
  decoded JSON types:

  ```go
  func outputVariants(tool types.Tool) []interface{} {
  	// v0.5: tool.OutputSchema.(map[string]interface{})["oneOf"]
  	variants, _ := tool.OutputSchema.(map[string]interface{})["anyOf"].([]interface{})
  	return variants
  }
  ```

- **Kind:** silent behavior change

### Provider error results are tool errors {#provider-tool-error-results}

- **What changed:** a provider tool result that reports an error (`IsError`
  true, for example an Anthropic `web_search_tool_result_error`) is now a
  `types.ToolErrorContent` part in `Content` (`Error` holds the provider's
  error value) and is replayed in the response messages as an `error-json`
  output, as TS `convertLanguageModelContent` maps `isError` results to
  `tool-error` parts. v0.5 kept a `ToolResultContent` with `IsError` and a
  `json` output, which the Anthropic converter could not send back as an
  error block. `GenerateText` and the legacy `ToolLoopAgent` changed.
  `StreamText` did this only for results that also set `Error`; a streamed
  provider result with only `IsError` set is now a tool error too (UI
  `tool-output-error`, not in `ToolResults`) (review rounds 71 and 72).
- **Am I affected?** Code that looks for `types.ToolResultContent` with
  `IsError` in `Content` or in the response messages, or for
  `ToolResult.IsError` on streamed `ChunkTypeToolResult` parts.
- **What to do:** read the tool-error part:

  ```go
  func providerErrors(content []types.ContentPart) []interface{} {
  	var out []interface{}
  	for _, part := range content {
  		// v0.5: types.ToolResultContent with IsError set
  		if te, ok := part.(types.ToolErrorContent); ok && te.ProviderExecuted {
  			out = append(out, te.Error)
  		}
  	}
  	return out
  }
  ```

- **Kind:** silent behavior change

### Streamed provider tool results carry the tool's metadata {#stream-provider-result-tool-metadata}

- **What changed:** a provider-executed tool result streamed by `StreamText`
  now carries its call's `ToolMetadata` (from `types.Tool.Metadata`): in
  `ToolResults()`, the step's `types.ToolResultContent` and the UI
  `tool-output-available` chunk's `toolMetadata`, as TS does and as
  `GenerateText` already did. v0.5 left it empty (review round 72).
- **Am I affected?** Code that reads `ToolMetadata` on streamed provider tool
  results, or UI clients that expect no `toolMetadata` on them.
- **What to do:** no action unless you depend on the empty field.
- **Kind:** silent behavior change

### Response messages replay tool errors and outputs like TS {#response-tool-error-replay}

- **What changed:** in `ResponseMessages`, a local tool error's `error-text`
  value is always a string, as TS `getErrorMessage`: `ErrorText` when set,
  else the string itself, `"unknown error"` for nil, `"Error: msg"` for an
  `error`, JSON text for anything else (v0.5 passed the raw `Error` value
  through). A provider-executed tool error's `error-json` value is the JSON
  round trip of `Error` (v0.6 betas used `ErrorText` when set). An approval
  request's `InputSchemaInput` is omitted when it equals the call input (TS
  `isDeepEqualData`). A tool output containing NaN or ±Inf replays with
  `null` in those positions (v0.5 replayed `null` for the whole output)
  (review round 72).
- **Am I affected?** Code that builds `types.ToolErrorContent` with a nil or
  non-string `Error` and reads the replayed `Output.Value`; code that reads
  `InputSchemaInput` from response messages; tool outputs with NaN/Inf
  floats.
- **What to do:** no action unless you read `Output.Value` of a replayed
  error as a non-string.
- **Kind:** silent behavior change

### ToolResults holds only successful calls {#tool-results-exclude-failures}

- **What changed:** `ToolResults`, `StaticToolResults` and
  `DynamicToolResults` of `GenerateTextResult`, `StreamTextResult`,
  `types.StepResult`, the step-end and end events, `AgentResult` and
  `NewStreamTextResultFromParts` results no longer hold failed calls (a tool
  execution error, an invalid or unknown tool call, a provider error result).
  A failed call is only a `types.ToolErrorContent` part in the step's
  `Content`; the model still gets it as an `error-text` / `error-json` tool
  result. TS `toolResults` holds only `tool-result` content parts (owner
  ruling, review round 71). Telemetry step-end events
  (`TelemetryStepEndEvent.ToolResults`) still include the failures, since
  that event has no content.
- **Am I affected?** Code that loops over `ToolResults` and checks
  `r.Error != nil`, or that expects one entry per tool call.
- **What to do:** read the failures from the content. The typed error is in
  `OnToolExecutionEnd`'s `ToolOutput.Error`:

  ```go
  func toolFailures(result *ai.GenerateTextResult) []string {
  	var failures []string
  	// v0.5:
  	// for _, r := range result.ToolResults {
  	// 	if r.Error != nil {
  	// 		failures = append(failures, r.ToolName+": "+r.Error.Error())
  	// 	}
  	// }
  	for _, part := range result.Content {
  		if te, ok := part.(types.ToolErrorContent); ok {
  			failures = append(failures, fmt.Sprintf("%s: %v", te.ToolName, te.Error))
  		}
  	}
  	return failures
  }
  ```

- **Kind:** silent behavior change

### Tool approval and tool-context errors fail the call {#tool-errors-fail-call}

- **What changed:** a tool context that fails the tool's `ContextSchema`, an
  approval function whose context fails it, an unknown approval status and an
  unsupported `ToolApproval` value now end `GenerateText` with an error (and
  error `StreamText`'s stream and the agents' runs), as in TS. v0.5 turned
  them into tool-error results the model saw. `GenerateText` also resolves
  every call's approval before running any tool. A tool's own `Execute` error
  is still a tool error.
- **Am I affected?** Tools with `ContextSchema:`, calls with `ToolApproval:`.
- **What to do:** fix the tool context or approval configuration, or handle
  the error:

  ```go
  // v0.5: the call succeeded; result.ToolResults[0].Error held the error
  // v0.6: the call fails with it
  var validationErr *providererrors.ValidationError
  _ = errors.As(err, &validationErr) // validationErr.Context.Field == "tool context"
  ```

- **Kind:** silent behavior change

- **Am I affected?** `PrepareStep` functions that return `ActiveTools` or

### Some provider tools are client-executed {#client-executed-provider-tools}

- **What changed:** OpenAI Responses computer, local shell, shell and

### Tool output NaN and Infinity become null in typed containers {#tool-output-non-finite-typed}

- **What changed:** a tool output whose typed map, slice or array

## Agents and approvals {#agents-and-approvals}

### A panicking ToolLoopAgent callback does not skip the other one {#agent-callback-panic-isolation}

- **What changed:** `ToolLoopAgent.Generate` and `Stream` run a settings-level
  callback (`AgentConfig.OnStart`, `OnStepStartEvent`, `OnToolExecutionStart`,
  `OnToolExecutionEnd`, `OnStepEndEvent`, `OnEndEvent`, `ErrorHandler`,
  `AbortHandler`) and the matching per-call callback each under its own
  recover. In v0.5 a panic in the settings-level callback skipped the per-call
  one. A panicking `AgentConfig.ErrorHandler` no longer crashes `Generate`,
  which returns the generation error instead. TS `mergeCallbacks` awaits
  `Promise.allSettled`, and `notify` ignores a throwing `onError`
  (tool-loop-agent.test.ts "should rethrow the generate error when onError
  throws", review round 72).
- **Am I affected?** Code that relies on a panic in an `AgentConfig` callback
  to stop the per-call callback, or on `ErrorHandler` panics propagating out
  of `Generate`.
- **What to do:** no action unless you panic in callbacks to signal failure.
  Record the failure instead and check it after the call.
- **Kind:** silent behavior change

### Kept approval responses reach the model without providerExecuted {#approval-response-prompt-shape}

- **What changed:** a tool approval response for a provider-executed call,
  which `GenerateText`, `StreamText` and the agents keep in the model prompt,
  now reaches the model as TS's LanguageModelV4 `tool-approval-response`
  part: `ApprovalID`, `Approved` and `Reason` only. v0.5 passed the response
  with `ProviderExecuted: true` and the caller's `ToolCallID` / `ToolCall`
  (TS convert-to-language-model-prompt.ts maps the kept part to
  `{approvalId, approved, reason}`; review round 73). The SDK's providers
  read only the approval ID and decision, so their requests are unchanged.
- **Am I affected?** A custom `provider.LanguageModel` that reads
  `ProviderExecuted`, `ToolCallID` or `ToolCall` of a
  `types.ToolApprovalResponseContent` in `opts.Prompt.Messages`.
- **What to do:** look the call up by `ApprovalID` from the assistant
  message's `types.ToolApprovalRequestContent`.
- **Kind:** silent behavior change

### Legacy ToolLoopAgent

These entries apply to the `Execute`, `ExecuteWithMessages` and
`GenerateAgent` loop of `pkg/agent`.

#### Legacy ToolLoopAgent approval IDs are generated {#legacy-approval-ids}

- **What changed:** the loop names each approval request, and the response of
  an automatic approval or denial, with the run's ID generator
  (`InternalOptions.GenerateID`, by default `aitxt-` plus 24 characters), as
  TS `generateId()`, and signs that ID. v0.5 used the tool call ID, which
  some providers repeat across steps. A step response without an ID also
  takes its ID from `InternalOptions.GenerateID`. Approvals persisted by v0.5
  still resume. `WorkflowAgent` keeps `approval-` plus the call ID.
- **Am I affected?** Code that answers an approval with the tool call ID.
- **What to do:** answer with the request's `ApprovalID`:

  ```go
  response := types.ToolApprovalResponseContent{ApprovalID: request.ApprovalID, Approved: true}
  _ = response // not request.ToolCallID
  ```

- **Kind:** silent behavior change

#### Legacy ToolLoopAgent tool results list provider results {#legacy-tool-results-provider}

- **What changed:** as `GenerateText` and TS `step.toolResults`,
  `StepResult.ToolResults` (with `StaticToolResults` /
  `DynamicToolResults`) and `AgentResult.ToolResults`, which
  `WorkflowAgent.Generate` returns too, hold the provider-executed results the
  model returned, before the local ones. A provider-executed call no longer
  adds a `null` result to the step.
- **Am I affected?** Code that treats every entry as a local execution.
- **What to do:** skip provider results:

  ```go
  for _, r := range result.ToolResults {
  	if r.ProviderExecuted {
  		continue // the provider's own result (web search, code execution, ...)
  	}
  	_ = r.Result
  }
  ```

- **Kind:** silent behavior change

#### Legacy ToolLoopAgent tool messages carry the output's JSON value {#legacy-tool-output-json-value}

- **What changed:** the `json` output of a tool result in the legacy loop's
  messages (`StepResult.ResponseMessages`, the next step's prompt) is now the
  tool output's JSON value (a struct becomes a map, a `json.Marshaler` its
  decoded value), as TS `createToolModelOutput` (`toJSONValue`) and as
  `GenerateText` already did. v0.5 put the Go value itself there (review
  round 71).
- **Am I affected?** Code that type-asserts `ToolResultOutput.Value` of tool
  messages from `AgentResult.Steps[i].ResponseMessages` or
  `WorkflowResult.Steps` to a Go type returned by a tool.
- **What to do:** no action unless you read that value as your Go type; read
  `types.ToolResult.Result` instead:

  ```go
  func toolOutputs(step types.StepResult) []interface{} {
  	var out []interface{}
  	for _, r := range step.ToolResults {
  		out = append(out, r.Result) // the Go value the tool returned
  	}
  	return out
  }
  ```

- **Kind:** silent behavior change

#### Legacy ToolLoopAgent request messages leave out the instructions {#legacy-request-messages}

- **What changed:** with `Include.RequestMessages`, a step's
  `Request.Messages` is the step's messages as TS `generateText` records
  them: no instruction messages, before prompt conversion.
  `WorkflowAgent.Generate` steps record the model prompt with its system
  message first, as TS WorkflowAgent.
- **Am I affected?** Code that reads the instructions from
  `Request.Messages[0]`.
- **What to do:** read the instructions from your own configuration.
- **Kind:** silent behavior change

#### The legacy ToolLoopAgent rejects a negative MaxRetries {#legacy-negative-maxretries}

- **What changed:** a negative `MaxRetries` (on the agent or from
  `PrepareCall`) fails the run with `*errors.InvalidArgumentError`
  ("maxRetries must be >= 0") before the model call, as TS `prepareRetries`.
  v0.5 silently made no retries.
- **Am I affected?** A negative `MaxRetries` on `AgentConfig` or a
  `PrepareCall` result.
- **What to do:** use 0 to disable retries.
- **Kind:** silent behavior change

#### A legacy ToolLoopAgent step timeout is context.DeadlineExceeded {#legacy-step-timeout-deadline}

- **What changed:** the per-step deadline (`Timeout.PerStep`, or a
  `PrepareCall` `Timeout` override, which now applies as in TS) reaches the
  model call as a deadline. A timed-out step fails with an error wrapping
  `context.DeadlineExceeded`. v0.5 surfaced `context.Canceled`.
- **Am I affected?** `errors.Is(err, context.Canceled)` used to detect a step
  timeout.
- **What to do:**

  ```go
  // v0.5
  if errors.Is(err, context.Canceled) { /* step timed out */ }
  // v0.6
  if errors.Is(err, context.DeadlineExceeded) { /* step timed out */ }
  ```

- **Kind:** silent behavior change

#### The legacy ToolLoopAgent step timeout covers tool execution {#legacy-step-timeout-tools}

- **What changed:** in v0.5 the per-step deadline (`Timeout.PerStep`) ended
  when the model call returned, so a tool could keep running past it. As in
  TS, the step timeout now also bounds the step's tools. A tool that used to
  finish after the step deadline is cancelled (its ctx is done), and the run
  ends with `context.DeadlineExceeded` before the next step, even if the tool
  ignored the cancellation.
- **Am I affected?** `Timeout.PerStep` on the legacy agent with tools that
  can run longer than the step.
- **What to do:** size `Timeout.PerStep` for the model call plus its tools, or
  use `Timeout.Total` or a timeout inside the tool.
- **Kind:** silent behavior change

#### An empty ActiveTools leaves no tools active in the legacy loop {#legacy-empty-active-tools}

- **What changed:** an empty, non-nil `ActiveTools` leaves no tools active,
  as TS `filterActiveTools` and `GenerateText`. v0.5 ignored it and sent every
  tool. A tool call against the empty set is a `NoSuchToolError` that
  `RepairToolCall` can repair.
- **Am I affected?** `ActiveTools: []string{}` on the legacy agent, or a
  filter that can return an empty slice.
- **What to do:** use nil to keep all tools.
- **Kind:** silent behavior change

#### The legacy ToolLoopAgent follows the PrepareCall tools, tool callers and output {#legacy-preparecall-tools-output}

- **What changed:** `GenerateAgent`, `Execute` and `ExecuteWithMessages` (and
  `WorkflowAgent.Generate`, which runs this loop) resolve tool search and
  `ExperimentalToolCallers` from the tools and tool callers that the first
  `PrepareCall` returns, and parse `AgentResult.Output` with the `Output` it
  returns. Its `ToolCallConcurrency` is validated before the run starts: an
  invalid value fails before `OnStart`, even when the model calls no tool,
  and an invalid configured value that `PrepareCall` replaces is no error.
  The output's `ParseCompleteOutput` gets the last step's usage. In v0.5 the
  loop used the configured tools, tool callers and output (a `ToolSearch`
  added by `PrepareCall` failed with "toolSearch must be bound by an AI SDK
  generation.") and passed the total usage. TS `ToolLoopAgent` passes the
  `prepareCall` result to `generateText`, which parses with
  `lastStep.usage`.
- **Am I affected?** `PrepareCall:` functions that set `Tools`,
  `ExperimentalToolCallers`, `ToolCallConcurrency` or `Output`, and
  `ParseCompleteOutput` implementations that read `opts.Usage`.
- **What to do:** no action unless your `PrepareCall` changes those fields
  and relied on the configured ones winning, or your output reads the usage.
  For the total usage, read `AgentResult.Usage`.
- **Kind:** silent behavior change

#### Legacy ToolLoopAgent steps carry the call ID {#legacy-step-call-id}

- **What changed:** each `types.StepResult` of the legacy loop now has
  `CallID` set to the run's call ID (the `CallID` of its `OnStartEvent` and
  `OnFinishEvent`), as TS step results' `callId` and as `GenerateText` steps
  already did. v0.5 left it empty. `WorkflowAgent.Generate` steps carry the
  workflow run's call ID (review round 70).
- **Am I affected?** Code that reads `StepResult.CallID` from
  `AgentResult.Steps`, `WorkflowResult.Steps` or the step lists of
  `OnStepStartEvent` / `OnFinishEvent`, or compares step results with
  `reflect.DeepEqual` against values without a `CallID`.
- **What to do:** no action unless you relied on an empty `CallID`.

- **Kind:** silent behavior change

#### The agent loop leaves provider-executed calls of unknown tools to the provider {#agent-provider-dynamic-unknown-tool}

- **What changed:** the legacy `ToolLoopAgent` loop (`Execute`,
  `GenerateAgent`, hence `WorkflowAgent.Generate`) no longer answers a
  provider-executed (dynamic) tool call whose tool is not in `Tools` with a
  `tool not found: <name>` error result, and no longer calls `OnToolError`
  for it. As in TS (`parseToolCall` keeps the call; only client calls run
  locally), it is the provider's call: the loop records a pending
  provider-executed result, as for a registered provider tool (review
  round 70).
- **Am I affected?** `OnToolError` callbacks or tool results that matched
  `tool not found:` for provider-executed (`ProviderExecuted: true`) calls.
- **What to do:** no action unless you relied on that error.

- **Kind:** silent behavior change

#### AI Gateway authentication errors are wrapped {#gateway-auth-error}

- **What changed:** `GenerateAgent`, `Execute` and `ExecuteWithMessages`
  return an unauthenticated AI Gateway error with the TS message that says how
  to authenticate, as `GenerateText`, `StreamText`, `GenerateObject`,
  `StreamObject` and the batch cancel/list calls do (TS `wrapGatewayError`).
  A telemetry integration's `OnStepError` now gets the wrapped error too, from
  `GenerateText`, `StreamText` and the legacy loop (TS notifies
  `onStepError` with `wrapGatewayError(error)`); its `OnError` keeps the
  original error.
- **Am I affected?** Code that matches the gateway error text, including in a
  `TelemetryIntegration.OnStepError` implementation.
- **What to do:** match with `errors.As` on
  `*gatewayerrors.GatewayAuthenticationError`.
- **Kind:** error text only

### WorkflowAgent

#### WorkflowAgent approval IDs are approval-toolCallId {#workflow-approval-ids}

- **What changed:** as in TS, `Generate` and `Stream` name the approval of

- **Am I affected?** Code that answers an approval with the tool call ID, or

- **What to do:** answer with the request's `ApprovalID`, as in the

#### Resumed approval results carry their model output {#workflow-resumed-output}

- **What changed:** the tool message holding resumed approvals' results (the

  held the raw `Result` and the input.
- **Am I affected?** Code that reads `.Result` or `.Input` from those parts.
- **What to do:** read `Output`:

#### WorkflowAgent PrepareStep overrides carry over to later steps {#workflow-preparestep-carryover}

- **What changed:** in `WorkflowAgent.Stream` / `StreamWithOptions`, the

## UI message streams {#ui-message-streams}

### UI message streams fail on an out-of-sequence chunk {#ui-out-of-sequence}

- **What changed:** when `CreateUIMessageStreamWithOptions` or
  `ToUIMessageStream` has an `OnEnd` or `OnStepEnd` callback, a chunk the
  message state cannot apply (a `text-delta` without its `text-start`, a tool
  result for an unknown tool call) ends the stream, as TS
  `processUIMessageStream`. The error channel carries a
  `*ai.UIMessageStreamError`, later chunks are not delivered, and `OnEnd`
  reports a failed outcome with that error. v0.5 passed the error to
  `OnError` and kept streaming. Without those callbacks the chunks are not
  checked, and `OnError` is no longer called for them, nor twice for an error
  chunk.
- **Am I affected?** Custom chunk producers with `OnEnd` / `OnStepEnd`.
- **What to do:** emit each part's start chunk before its deltas, and treat a
  `*ai.UIMessageStreamError` on the error channel as the stream's failure:

  ```go
  var uiErr *ai.UIMessageStreamError
  if errors.As(err, &uiErr) {
  	// a chunk arrived out of sequence
  }
  ```

- **Kind:** silent behavior change

### An out-of-range KeepAliveMs is an error {#keep-alive-range}

- **What changed:** a `UIMessageStreamResponseInit.KeepAliveMs` that points to
  zero, a negative duration or more than 2147483647ms makes the
  `Create*` / `Pipe*` UI message stream response helpers return
  `keepAliveMs must be a positive finite timer duration no greater than
  2147483647` before writing anything, as TS `createSseStreamWithKeepAlive`
  throws. v0.5 turned keep-alive off for zero or negative values. A nil
  `KeepAliveMs` is unchanged.
- **Am I affected?** `KeepAliveMs` set to a pointer to 0 or a negative value
  to turn keep-alive off.
- **What to do:** leave it nil:

  ```go
  init := &ai.UIMessageStreamResponseInit{} // KeepAliveMs nil: no keep-alive
  ```

- **Kind:** silent behavior change

### UI message state follows TS for four chunk edge cases {#ui-message-state-edge-cases}

- **What changed:** the message that `OnEnd`, `OnStepEnd` and
  `ReadUIMessages` build keeps a tool part's own `title` when a
  `tool-output-available` or `tool-output-error` chunk carries one (TS passes
  the invocation's title), keeps an empty `id` on a reasoning part, keeps the
  earlier finish reason when a `finish` chunk has `"finishReason": null`, and
  leaves `input` out of a tool part that never received one (v0.5 set it to
  JSON `null`): a streaming tool part whose partial input cannot be parsed, a
  `tool-output-available` or `tool-output-error` chunk for such a part, and a
  `tool-input-available` or `tool-input-error` chunk with no `input` key
  (review round 68). TS `processUIMessageStream` does each of these.
- **Am I affected?** Only if you write such chunks yourself (through
  `UIMessageStreamWriter.Write` or a merged stream) and read the built
  message's parts, for example `part["title"]` or `part["input"] == nil`.
- **What to do:** no action unless you relied on a chunk title replacing the
  part's title or on a `null` partial input. Check for a missing key:

  ```go
  func hasInput(part map[string]interface{}) bool {
  	_, ok := part["input"] // v0.5: present with a nil value
  	return ok
  }
  ```

- **Kind:** silent behavior change

### ToUIMessageStream OnEnd reports the finish chunk's reason {#ui-on-end-finish-reason}

- **What changed:** the `finishReason` that `ToUIMessageStream` (and
  `StreamTextResult.ToUIMessageStream`) passes to `OnEnd`/`OnFinish` is the
  reason of the `finish` chunk the stream sent. With `SendFinish: false`, or
  when the stream fails before its `finish` chunk, it is now empty
  (`types.FinishReason("")`); v0.5 passed the source's last step or call
  reason. TS `handleUIMessageStreamFinish` passes `state.finishReason`,
  which only a `finish` chunk sets. The value is still a `types.FinishReason`.
- **Am I affected?** `OnEnd:` or `OnFinish:` callbacks on a UI message
  stream with `SendFinish: false` (for example a stream you merge into
  another) that read `e["finishReason"]`.
- **What to do:** no action unless you do that. Read the reason from the
  result instead:

  ```go
  func finishReason(result *ai.StreamTextResult) types.FinishReason {
  	return result.FinishReason() // v0.5: OnEnd's e["finishReason"] with SendFinish false
  }
  ```

- **Kind:** silent behavior change

### One error chunk for a StreamText run that ends with an error part {#ui-single-error-chunk}

- **What changed:** when a `StreamText` run ends with an `error` part (the
  model call fails to open, the run fails before its first model stream, a
  later step fails to prepare or open, or the model stream ends without
  output), `StreamTextResult.ToUIMessageStream`, `CreateUIMessageStream` and
  the UI message stream response helpers write that part's `error` chunk
  only (and, for a later step that fails to start, no `finish` chunk after
  it; see [UI finish and abort](#ui-finish-and-abort-chunks)). v0.5 wrote a second `error` chunk for the same error when the stream
  closed with it (review round 69). TS `streamText` closes its stream
  normally after such a part, so `toUIMessageStream` writes one. The error
  channel still carries the error, and `OnEnd` still reports a failed
  outcome.
- **Am I affected?** Clients or tests that count `"type":"error"` chunks in a
  UI message stream, or expect two of them for one failed run.
- **What to do:** no action unless you count error chunks. Expect one:

  ```go
  func errorChunks(chunks <-chan ai.UIMessageChunk) int {
  	n := 0
  	for c := range chunks {
  		if c["type"] == "error" {
  			n++ // v0.5: two for a run that ended with an error part
  		}
  	}
  	return n
  }
  ```

- **Kind:** wire/protocol change

### UI message streams end like the source stream {#ui-finish-and-abort-chunks}

- **What changed:** `StreamTextResult.ToUIMessageStream`,
  `CreateUIMessageStream`, `ToUIMessageStream` and the UI response helpers
  write a `finish` chunk only when a StreamText source has its call-level
  `finish` part (a later step that fails to start ends with its `error`
  chunk). A run that ends with an `abort` part writes one `abort` chunk.
  v0.5 wrote a second one when the stream then closed with the abort error.
  A source that ends after an `abort` part gets nothing more (v0.5 added an
  error chunk, `finish-step` and `finish`), and its `OnEnd` outcome is
  `aborted`. TS writes `finish` for a `finish` part only and records an
  `abort` part as the aborted outcome (review round 70). A raw provider
  stream passed to `ToUIMessageStream` still gets a synthesized `finish`.
- **Am I affected?** Clients or tests that expect a `"type":"finish"` chunk
  after an error, or count `"type":"abort"` chunks.
- **What to do:** no action unless you do that. Treat `error` or `abort` as
  the end:

  ```go
  func ended(c ai.UIMessageChunk) bool {
  	switch c["type"] {
  	case "finish", "error", "abort":
  		return true // v0.5: a finish chunk followed every StreamText run
  	}
  	return false
  }
  ```

- **Kind:** wire/protocol change

### UI file chunks carry the file's provider metadata {#ui-file-provider-metadata}

- **What changed:** the UI `file` and `reasoning-file` chunks now include

### ToUIMessageStream maps start-led part sequences one to one {#ui-start-part-one-to-one}

- **What changed:** when the source given to `ai.ToUIMessageStream` starts
  with a `provider.ChunkTypeStart` part (a `StreamText`, harness or
  `NewStreamTextResultFromParts` stream, or your own part slice), each part
  now maps to its UI chunk as in TS `toUIMessageStream`. The start part
  writes the `start` chunk and the finish part writes the `finish` chunk
  where it occurs. Nothing is added at the end: no closing `text-end` /
  `reasoning-end`, no `finish-step` for the `finish` part, no `finish` when
  the source has no finish part, and no incomplete-stream `error` chunk. v0.5
  framed these sources like raw provider streams. `NewStreamTextResultFromParts`
  streams (`Stream()`, `FullStream()`) now begin with a `ChunkTypeStart` part,
  as TS `HarnessStreamTextResult` does. A raw provider stream (no leading
  start part) keeps its framing, but its `start` chunk is now written after
  the first source chunk arrives (owner ruling 2026-10-30, review round 71).
- **Am I affected?** `ai.ToUIMessageStream(` on part slices or streams that
  begin with `provider.ChunkTypeStart`; code that reads
  `NewStreamTextResultFromParts(` results' `Stream()` / `FullStream()` and
  expects `ChunkTypeStartStep` first.
- **What to do:** no action unless you rely on the added chunks. Send
  `ChunkTypeFinishStep` and `ChunkTypeFinish` parts yourself, and skip a
  leading start part:

  ```go
  func firstStepPart(s provider.TextStream) (*provider.StreamChunk, error) {
  	for {
  		c, err := s.Next()
  		if err != nil || c.Type != provider.ChunkTypeStart {
  			return c, err
  		}
  	}
  }
  ```

- **Kind:** wire/protocol change

  a `Tracer` uses `otel.Tracer("ai")`, and the GenAI `OpenTelemetry`
  integration uses `otel.Tracer("gen_ai")`. v0.5 used `"ai-sdk"` for root
  spans and `"go-ai"` for child spans. Every span of a call now comes from the
  root's tracer, including a `Tracer` you pass. `telemetry.TracerName` is
  deprecated and unused.
- **Am I affected?** Instrumentation-scope filters or sampler rules that match
  `ai-sdk` or `go-ai`.
- **What to do:** match the new names, or pass your own `Tracer`:

  ```go
  // v0.5: spans had the instrumentation scope "ai-sdk" or "go-ai"
  // v0.6: "ai" (legacy) or "gen_ai" (GenAI), or your own tracer's name
  legacyScope, genAIScope := telemetry.LegacyTracerName, telemetry.GenAITracerName
  _, _ = legacyScope, genAIScope
  ```

- **Kind:** wire/protocol change

### EnrichSpan and runtime context attributes follow TS {#enrich-span-attributes}

- **What changed:** an `EnrichSpan` value that is an object, a struct, `nil`
  or a mixed-type array is now dropped (TS `sanitizeAttributes`). v0.5 wrote
  it as a JSON string attribute. A `[]interface{}` of one primitive type
  becomes a typed slice attribute, and Go's other integer and float kinds stay
  numbers. A runtime context value that is an object (any string-keyed map, a
  struct or a pointer to one) is flattened into
  `ai.settings.context.<path>` attributes instead of one JSON string.
- **Am I affected?** Dashboards or queries that read those JSON-string
  attributes.
- **What to do:** read the flattened keys, or return primitives from
  `EnrichSpan`.
- **Kind:** wire/protocol change

### Evaluate telemetry and event names are decide names {#decide-telemetry-names}

- **What changed:** with the evaluate-to-decide rename, span and attribute
  names are `ai.decide*` and `ai.decision.*`, the GenAI operation is
  `gen_ai.operation.name=decide`, and the diagnostic channel events are
  `experimental_onDecideStart`, `experimental_onDecideEnd`,
  `experimental_onDecisionModelCallStart` and
  `experimental_onDecisionModelCallEnd`. The deprecated
  `DiagnosticEventOnEvaluate*` constants now hold the decide values.
- **Am I affected?** Queries, dashboards or diagnostic subscribers that match
  the evaluate names.
- **What to do:** match the decide names.
- **Kind:** wire/protocol change

### A cancelled GenerateText reports OnError to telemetry {#generate-cancel-telemetry}

- **What changed:** a cancelled or timed-out `GenerateText` (and the legacy
  `ToolLoopAgent` loop) reports `OnError`, not `OnAbort`, to telemetry
  integrations, as TS `generateText` has no abort telemetry. The root and step
  spans carry the error status. `GenerateTextOptions.OnAbortEvent` /
  `OnAbort` still fire.
- **Am I affected?** Custom telemetry integrations that count aborts in
  `OnAbort` for `GenerateText`.
- **What to do:** handle the cancellation in the integration's `OnError`.
- **Kind:** silent behavior change

### Step-start events report the call's tools and the output {#step-start-call-tools}

- **What changed:** `OnStepStartEvent.Tools` of `GenerateText`, `StreamText`,
  `ToolLoopAgent.Generate` / `Stream` and the legacy `GenerateAgent` /
  `Execute` loop is the call's tool set. In v0.5 it was the step's narrowed
  set (after `ActiveTools`, `FilterActiveTools`, tool search and tool-caller
  routing). `OnStepStartEvent.Output` is now the call's output specification;
  v0.5 left it nil. TS `stepStartEvent.tools` is "the tools available for
  this generation", and `stepStartEvent.output` is the output.
- **Am I affected?** `OnStepStart:` callbacks (and `OnStepStartEvent:` in
  `AgentConfig`) that read `e.Tools` or expect `e.Output` to be nil.
- **What to do:** read `e.ActiveTools` for the step's limit, or read the
  tools sent to the model from `OnLanguageModelCallStart`:

  ```go
  opts := ai.GenerateTextOptions{
  	OnLanguageModelCallStart: func(ctx context.Context, e ai.LanguageModelCallStartEvent) {
  		sent := e.Tools // v0.5: OnStepStartEvent.Tools
  		_ = sent
  	},
  }
  _ = opts
  ```

- **Kind:** silent behavior change

### Telemetry OnStepError fires for every failed step {#telemetry-step-error}

- **What changed:** a telemetry integration's `OnStepError` now runs, before
  `OnError`, for every `GenerateText` or `StreamText` step that fails after
  it started. In v0.5 it ran only when the model call failed to open; any
  other failure closed the step span through `OnError` alone. Now it also
  runs for a `GenerateText` tool choice violation, tool approval or
  tool-context error, or parse or download failure after the model call, and
  for a `StreamText` step whose model stream fails mid-step, ends without
  output, or whose tool input callback, download or conversion fails. TS
  `generateText` and `streamText` notify telemetry `onStepError` for the open
  step on every failure (`notifyStepError`). The error is wrapped for an
  unauthenticated AI Gateway request (see
  [Gateway auth error](#gateway-auth-error)); `OnError` keeps the error
  itself.
- **Am I affected?** Custom `TelemetryIntegration` implementations with an
  `OnStepError` method that assume it only runs when a model call fails to
  open, or that compare its `e.Error` with the provider's error by `==` or by
  text.
- **What to do:** no action unless your integration does that. Match errors
  with `errors.As`:

  ```go
  func isGatewayAuth(err error) bool {
  	var auth *gatewayerrors.GatewayAuthenticationError
  	return errors.As(err, &auth) // also true for the wrapped error
  }
  ```

- **Kind:** silent behavior change

### Telemetry step-end, end, tool-end, error and abort run after the callbacks {#telemetry-callback-order}

- **What changed:** `GenerateText` and `StreamText` now call the user
  callbacks before the telemetry integrations for the same event: the step's
  `OnStepEnd` / `OnStepEndEvent` before the integration `OnStepEnd`, `OnEnd`
  / `OnEndEvent` before the integration `OnFinish` (onEnd), and
  `OnToolExecutionEnd` before the integration `OnToolExecutionEnd`. v0.5 ran
  the telemetry first for both end events, for the `StreamText` step end and
  for every tool end (the `GenerateText` step end already ran the callbacks
  first). `GenerateObject`, `StreamObject`, `ExperimentalDecide` and the
  legacy `ToolLoopAgent` (also `WorkflowAgent.Generate`) follow the same
  order: `OnStepEnd` before the telemetry step end, `OnEnd` before the
  telemetry end, `OnToolExecutionEnd` before the telemetry tool end,
  `OnStepError` before the telemetry step error, and `ExperimentalDecide`'s
  `OnStart` before the telemetry `OnDecideStart`. `WorkflowAgent` likewise
  calls `OnToolExecutionEnd` of an approval-resumed tool, `OnError` and
  `OnAbort` before the root telemetry `OnToolExecutionEnd`, `OnError` and
  `OnAbort`. `StreamObject` now parses and repairs the final JSON (calling
  `RepairText`) before `OnStepEnd`, and a `ToModelOutput` failure still calls
  `OnToolExecutionEnd` (with the raw output) before the call fails. TS
  `notify([callback, telemetry.onX])` starts the callback first, and TS
  WorkflowAgent awaits its callbacks before the telemetry dispatcher (review
  rounds 70 and 71). `OnStepError` also runs before the telemetry
  `OnStepError` (see [Later step failure](#streamtext-continuation-failure-end)).
- **Am I affected?** Telemetry integrations whose `OnStepEnd`, `OnFinish`,
  `OnToolExecutionEnd`, `OnError` or `OnAbort` shares state with your
  `OnStepEnd`, `OnEnd`, `OnEndEvent`, `OnToolExecutionEnd`, `OnError` or
  `OnAbort` callbacks and depends on running first, for example a span the
  callback expects to be ended already. `RepairText` and `OnStepEnd` of
  `StreamObject` that depend on their order; `OnToolExecutionEnd` callbacks
  that assume a `ToModelOutput` failure never reaches them.
- **What to do:** no action unless you rely on that order. Do the work that
  must come last in the integration:

  ```go
  type lastRecorder struct {
  	telemetry.NoopTelemetryIntegration
  }

  func (lastRecorder) OnFinish(ctx context.Context, e telemetry.TelemetryFinishEvent) {
  	// runs after OnEnd / OnEndEvent (v0.5: before them)
  }
  ```

- **Kind:** silent behavior change

### Telemetry step end runs every OnStepEnd before the deprecated OnStepFinish {#telemetry-step-finish-fanout}

- **What changed:** `FireOnStepEnd` / `FireOnStepFinish` call `OnStepEnd` on
  every integration, then `OnStepFinish` on the integrations that still
  implement it, each under its own recover. v0.5 called both per integration
  in turn, so a panicking `OnStepEnd` skipped that integration's
  `OnStepFinish`. TS dispatcher `onStepEnd: mergeCallbacks(onStepEnd,
  onStepFinish)` (review round 72).
- **Am I affected?** Integrations that implement the deprecated
  `OnStepFinish` and depend on it running right after their own `OnStepEnd`,
  before other integrations' `OnStepEnd`.
- **What to do:** no action unless you depend on that order. Implement
  `OnStepEnd` only.
- **Kind:** silent behavior change

### Rerank telemetry `ai.ranking` uses TS keys {#telemetry-ranking-keys}

- **What changed:** v0.5 wrote each `ai.ranking` entry on the
  `ai.rerank.doRerank` span as `{"Index":2,"RelevanceScore":0.9}`; v0.6
  writes `{"index":2,"relevanceScore":0.9}`, as TS
  `JSON.stringify(ranking entry)` does (LegacyOpenTelemetry, and
  OpenTelemetry with `Reranking`) (review round 73).
- **Am I affected?** Dashboards or tests that parse the `ai.ranking` span
  attribute.
- **What to do:** read `index` and `relevanceScore`.
- **Kind:** silent behavior change

### GenAI embeddings span operation name is `embeddings` {#telemetry-embeddings-operation-name}

- **What changed:** v0.5 set `gen_ai.operation.name` on the OpenTelemetry
  (GenAI) `embeddings <model>` child span of `Embed` / `EmbedMany` to
  `ai.embed.doEmbed` / `ai.embedMany.doEmbed`; v0.6 sets `embeddings`, as TS
  `open-telemetry.ts` `onEmbedStart` does (review round 74). The span name
  and the root span are unchanged.
- **Am I affected?** Dashboards, queries or tests that filter the GenAI
  `embeddings` span by `gen_ai.operation.name`.
- **What to do:** match `gen_ai.operation.name = "embeddings"`.
- **Kind:** silent behavior change

## Errors {#errors}

### Errors are returned without Go prefixes {#errors-unprefixed}

- **What changed:** errors are returned as is, without Go-added prefixes such
  as "... failed at step N:", "generation failed:", "output parsing failed:"
  or "failed to start stream:". `InvalidArgumentError` text is now
  `Invalid argument for parameter <field>: <message>`, and
  `TypeValidationError` text is on one line.
- **Am I affected?** `strings.Contains(err.Error(), ...)` checks or tests that
  compare error text.
- **What to do:** match with `errors.As` / `errors.Is`.
- **Kind:** error text only

### Error messages quote names as TS does {#error-name-quoting}

- **What changed:** messages that quote a tool, model, question or separator
  name (`CreateIDGenerator`, `ExperimentalToolCallers`, tool search,
  `ExperimentalStreamTranscribe`, decision validation,
  `DecisionUnsupportedQuestionTypeError`) put the name between plain double
  quotes instead of Go `%q` escaping. The text changes only for a name with
  `"`, `\`, non-ASCII or control characters. The download URL check
  (`CreateURLDownload`, `GenerateVideo` downloads) writes a blocked hostname
  without quotes, as TS: `URL with hostname printer.local is not allowed`
  (v0.5: `"printer.local"`).
- **Am I affected?** Code that compares these messages.
- **What to do:** match these errors with `errors.As`, not by their text.
- **Kind:** error text only

### An unknown decision model ID is a NoSuchModelError {#decide-unknown-model}

- **What changed:** `ExperimentalEvaluate` and `ExperimentalDecide` with a
  string `Model` whose provider returns no model fail with
  `*providererrors.NoSuchModelError` (`ModelType: "decisionModel"`, message
  `No such decisionModel: <id>`), as TS `resolveDecisionModel`. v0.5 returned
  a plain error, `no such evaluationModel: <id>`. The adapter from
  `provider.AdaptEvaluationModelProvider` reports a missing model the same
  way.
- **Am I affected?** Code that compares an `ExperimentalEvaluate` or
  `ExperimentalDecide` error with `no such evaluationModel`.
- **What to do:** match the type (`errors.Is(err, providererrors.ErrModelNotFound)`
  also matches):

  ```go
  var nsm *providererrors.NoSuchModelError
  if errors.As(err, &nsm) {
  	log.Printf("unknown decision model %s", nsm.ModelID)
  }
  ```

- **Kind:** error text only

### Registry resolution errors follow the TS registry {#registry-resolution-errors}

- **What changed:** the `registry` resolvers return the errors TS
  `createProviderRegistry` throws:
  - A provider with no video or decision factory (`ResolveVideoModel`,
    `ResolveDecisionModel`, `ResolveEvaluationModel`) is a
    `*providererrors.NoSuchModelError` with the full registry ID
    (`ModelID: "provider:model"`, message `No such videoModel: provider:model`).
    v0.5 returned `*registry.NoSuchProviderError`.
  - A provider factory that returns a nil model with a nil error is the same
    `NoSuchModelError`, for every model type. v0.5 returned the nil model with
    a nil error.
  - An unknown provider is still a `*registry.NoSuchProviderError`, and
    `errors.As` with a `*providererrors.NoSuchModelError` target and
    `errors.Is` with `providererrors.ErrModelNotFound` now also match it (TS
    `NoSuchProviderError` extends `NoSuchModelError`). Its
    `ModelID` is the provider ID, as TS `getProvider` sets it (v0.5: the model
    part of the ID; empty from `GetProvider`). `Files` and `Skills` report
    `ModelType: "languageModel"` (v0.5: `"files"` / `"skills"`).
  - `Files` / `Skills` on a registered provider without that capability
    return the TS text with the Go method name, `The provider "x" does not
    support file uploads. Make sure it exposes a Files() method.` (and
    `... does not support skills. Make sure it exposes a Skills() method.`).
    v0.5: `No such provider: x (provider "x" does not support file uploads;
    make sure it exposes a Files() method; available providers: ...)`. The
    error is still a `*registry.NoSuchProviderError` (with `Reason` set), and
    it matches neither `NoSuchModelError` nor `ErrModelNotFound` (TS throws a
    plain `Error`).
- **Am I affected?** `errors.As(err, &nsp)` with `*registry.NoSuchProviderError`
  after `ResolveVideoModel` / `ResolveDecisionModel` / `ResolveEvaluationModel`;
  `errors.As` checks for `*providererrors.NoSuchModelError` or
  `errors.Is(err, providererrors.ErrModelNotFound)` placed before a
  `NoSuchProviderError` check; reads of `NoSuchProviderError.ModelID` or
  `.ModelType` (including after `GetProvider`); matches on the text of a
  `Files` / `Skills` error (`does not support file uploads`); code that checks
  a resolved model for nil.
- **What to do:** check for the provider error first, then the model error:

  ```go
  var nsp *registry.NoSuchProviderError
  var nsm *providererrors.NoSuchModelError
  switch {
  case errors.As(err, &nsp):
  	log.Printf("unknown provider %s", nsp.ProviderID)
  case errors.As(err, &nsm):
  	log.Printf("no %s %s", nsm.ModelType, nsm.ModelID)
  }
  ```

- **Kind:** silent behavior change

### Non-JSON error bodies use the HTTP status text {#non-json-error-body}

- **What changed:** a non-2xx response with an empty or non-JSON body uses the
  HTTP status text as `ProviderError.Message` (for example `Bad Gateway`).
  The body stays in `ResponseBody`.
- **Am I affected?** Code that reads the body from `Message`.
- **What to do:** read `StatusCode` and `ResponseBody`.
- **Kind:** error text only

### Unparsable structured output has a JSONParseError cause {#object-parse-json-parse-error}

- **What changed:** when `GenerateObject`, `StreamObject` or an `Output`
  cannot parse the model's text, the `NoObjectGeneratedError.Cause` (and the
  error `RepairText` receives) is a `*providererrors.JSONParseError` holding
  the text, instead of the raw `*json.SyntaxError`. The parser error is its
  `Unwrap()`. TS: `NoObjectGeneratedError.cause` is a `JSONParseError`
  (review round 72).
- **Am I affected?** Code that type-asserts `Cause.(*json.SyntaxError)` or
  compares the cause or the `RepairText` error directly. `errors.As` with
  `*json.SyntaxError` still works.
- **What to do:** match with `errors.As`:

  ```go
  func isUnparsable(err error) bool {
  	var nog *ai.NoObjectGeneratedError
  	if !errors.As(err, &nog) {
  		return false
  	}
  	// v0.5: _, ok := nog.Cause.(*json.SyntaxError)
  	return providererrors.IsJSONParseError(nog.Cause)
  }
  ```

- **Kind:** silent behavior change

### Output validation failures have a TypeValidationError cause {#output-type-validation-cause}

- **What changed:** when the value an `ObjectOutput`, `ArrayOutput` or
  `ChoiceOutput` parsed fails validation (schema, missing `elements` or
  `result`, array length, an element, or a choice not in the options), the
  `NoObjectGeneratedError.Cause` is a `*providererrors.TypeValidationError`
  holding the value, as in TS. Its text is `Type validation failed: Value:
  <json>.\nError message: <reason>`. v0.5 used the validator's error or a
  plain error, and the choice reason now ends with a period, as in TS. The
  validator's error is still the cause's `Unwrap()` (review round 73).
- **Am I affected?** Code that type-asserts or compares
  `NoObjectGeneratedError.Cause` from `GenerateText` / `StreamText` with an
  `Output`, or matches its text.
- **What to do:** match with `errors.As`:

  ```go
  func isInvalidOutput(err error) bool {
  	var nog *ai.NoObjectGeneratedError
  	var tve *providererrors.TypeValidationError
  	return errors.As(err, &nog) && errors.As(nog.Cause, &tve)
  }
  ```

- **Kind:** silent behavior change

## Providers {#providers}

### All providers

#### Provider IDs follow TS config.provider {#provider-ids}

- **What changed:** `Provider()` on models returns the TS `config.provider`
  value: `groq.chat`, `mistral.embedding`, `openai.image` and so on. v0.5
  returned the bare provider name. Telemetry `ai.model.provider` and
  `SerializedModel.Provider` change accordingly. Provider option and metadata
  keys do not change, and payloads serialized by earlier versions still
  restore.
- **Am I affected?** `model.Provider() == "groq"` and similar comparisons,

- **What to do:** compare the prefix:

  ```go
  isGroq := strings.HasPrefix(model.Provider(), "groq")
  _ = isGroq
  ```

#### Responses and stream chunks are validated {#response-validation}

- **What changed:** about 25 more providers reject a 2xx body that does not

  Cohere's legacy plain-array `embeddings`.
- **Am I affected?** Custom base URLs, proxies or mock servers that return

- **Kind:** silent behavior change

#### Invalid provider options fail the call {#provider-options-validation}

- **What changed:** `result.Content` from Anthropic, Bedrock and Google keeps

- **Am I affected?** Code that reads `Content` by index.
- **What to do:** switch on each part's type instead of its position.
- **Kind:** silent behavior change

#### Empty stop sequences are sent {#empty-stop-sequences}

- **What changed:** an explicitly empty `StopSequences` (`[]string{}`) is now
  sent as an empty list by the AI Gateway (`stopSequences: []`), Groq,

- **What to do:** no action unless an API rejects the empty list; pass nil

### AI Gateway

#### Provider tools reach the AI Gateway as provider tools {#gateway-provider-tools}

- **What changed:** the Anthropic provider tools (`pkg/providers/anthropic/tools`,
  all 23 constructors), the OpenAI tools (`openaitool.*`, `CustomTool.ToTool`,
  `responses.NewLocalShellTool`, `NewShellTool`, `NewApplyPatchTool`,
  `NewComputerTool`, `NewProgrammaticToolCallingTool`) and the xai tools
  (`xai.WebSearch`, `XSearch`, `CodeExecution`, `ViewImage`, `ViewXVideo`,
  `ImageGeneration`, `FileSearch`, `MCPServer`) now carry the TS provider tool
  identity: `Type: types.ToolTypeProviderDefined` (`"provider"`),
  `ProviderID` (the TS id, equal to the tool `Name`, for example
  `anthropic.web_search_20250305`) and `ProviderArgs` (the TS camelCase args,
  for example `{"maxUses": 3, "allowedDomains": ["example.com"]}`; `{}` for
  tools without config). A gateway model sends them as provider tools
  (`{type: "provider", id, name, args}`) as TS does; v0.5 sent them as
  function tools named `anthropic.*` / `openai.*` / `xai.*`, which the routed
  model treated as client functions. The xai MCP args include
  `authorization`, as TS sends it. The google tools (`GoogleSearchTool`,
  `CodeExecutionTool`, ...) now have a `Name` (`google_search`,
  `code_execution`, ...), so the gateway gets a non-empty tool name, and are
  `ProviderExecuted` with TS's input schemas. Other effects, all as in TS:
  chat models of other providers (and Bedrock, for non-Anthropic provider
  tools) drop these tools with an `unsupported` `provider-defined tool <id>`
  warning instead of sending them as functions; the Mistral conversation
  model drops every non-Mistral provider tool; realtime tool definitions skip
  them; telemetry tool definitions (`gen_ai.tool.definitions`) record
  `{type: "provider", name, id, args}`; an Anthropic Message Batch that
  contains `ComputerToolset20260801()` fails with
  `UnsupportedFunctionalityError` (its calls come back named `computer`);
  `ComputerToolset20260801` rejects an unknown member in its configs with a
  `TypeValidationError`; an Anthropic, OpenAI or xai provider tool given only
  `Type` / `ProviderID` / `ProviderArgs` (for example after
  `workflow.ResolveSerializableTools`) is now sent with its configuration
  instead of dropped as unsupported or sent bare. Direct Anthropic, OpenAI
  Responses and xai requests are unchanged (review round 73).
- **Am I affected?** Gateway models with `anthropic/tools`, `openai/tool`,
  `responses.New*Tool()` or `xai` tool constructors or the google tools; code
  that reads `Tool.Type`, `ProviderID`, `ProviderArgs`, `Name` or
  `ProviderExecuted` of those tools (`Tool.Type == "provider"` checks);
  these tools passed to other providers or to realtime models;
  `ExperimentalBatch` requests with `ComputerToolset20260801`.
- **What to do:** no action.
- **Kind:** wire/protocol change

#### AI Gateway tools have no title {#gateway-tool-title}

- **What changed:** `tools.NewExaSearch`, `NewParallelSearch`,
  `NewPerplexitySearch`, `NewTakoSearch`, `NewBrowserbaseSearch` and
  `NewBrowserbaseFetch` (`pkg/providers/gateway/tools`) no longer set

  ```go
  }

  func main() {
  	fmt.Println(exaSearchWithTitle().Title)
  }
  ```

- **Kind:** silent behavior change

#### Gateway tool outputs without a value {#gateway-tool-output-null}

- **What changed:** a tool result whose output value is nil (a tool that
  returned nothing: `{Type: "json", Value: nil}`) reaches the AI Gateway as
  `{type: "json", value: null}`, as TS; an empty `content` output is sent with
  `value: []`. v0.5 omitted `value`, which the gateway's prompt schema
  requires (review round 74).
- **Am I affected?** Gateway models with tools that return nil, or `content`
  tool outputs without parts.
- **What to do:** no action.
- **Kind:** wire/protocol change

### Anthropic

#### Anthropic provider tools are matched by id {#anthropic-provider-tool-id}

- **What changed:** the Anthropic provider now selects provider tools by
  their id (`Tool.ProviderID` for `Type: "provider"` tools, else `Tool.Name`),
  as TS does with `tool.id`, and treats `Tool.Name` as the caller's tool name
  (TS: the tools record key). A provider tool under a custom name (a
  constructor tool with `Name` changed, or a TS-shaped

  (`types.Tool{Name: "anthropic.web_search_20260209"}`) is now sent with empty
  args instead of dropped; only unknown ids warn. A TS-shaped advisor tool
  without a `model` string fails with `*TypeValidationError`. The "code
  execution tool is required when using skills" warning checks the tool id.
  `ExperimentalBatch` rejects a provider tool whose custom name differs from
  its Anthropic wire name (`UnsupportedFunctionalityError`, "aliased provider
  tool names in batches"), as TS; tools keeping the constructor's id as their
  name are still accepted. `prompt.AnthropicToolsetNames` finds a renamed

#### openaitool.ToolSearch keeps the search schema in its options {#openai-tool-search-parameters}

- **What changed:** `openaitool.ToolSearch(...)` sets the tool's

  schema (`ToolSearchArgs.Parameters`) is in the new

- **What to do:** read the search schema from the options:

  ```go
  func searchSchema(tool types.Tool) map[string]interface{} {
  	// v0.5: tool.Parameters.(map[string]interface{})
  	opts, _ := tool.ProviderOptions.(openaitool.ToolSearchOptions)
  	return opts.Parameters
  }
  ```

- **Kind:** silent behavior change

## MCP {#mcp}

### MCP OAuth rejects unbound pre-registered confidential credentials {#mcp-oauth-issuer}

- **What changed:** client information with a client secret (or a custom
  authenticator) but no `Issuer` and no stored authorization server
  information fails `mcp.Auth` with an authorization-server mismatch error
  (TS #23579). v0.5 skipped the check. Dynamically registered clients keep
  working.
- **Am I affected?** Pre-registered confidential OAuth clients without
  `Issuer`.
- **What to do:** set `Issuer` to the authorization server the secret was
  registered with, or return it from
  `OAuthAuthorizationServerInformationStore`.
- **Kind:** silent behavior change

### MCP clients have no default request timeout {#mcp-no-default-timeout}

- **What changed:** `MCPClientConfig.RequestTimeoutMS` and the transports'
  `TimeoutMS` default to no timeout, as TS fetch; the caller's ctx governs.
  v0.5 used 30 seconds. JSON-RPC request IDs start at 0,
  `MCPClientError.Error()` is the bare message, and the HTTP and stdio
  transports probe `server/discover` first.
- **Am I affected?** MCP clients that relied on the 30 s default.

  ```go
  cfg := mcp.MCPClientConfig{RequestTimeoutMS: 30000} // v0.5 default
  ```

## Code mode {#code-mode}

### Code mode has a default 10 s CPU limit {#codemode-cpu-limit}

- **What changed:** `ExecutionPolicy.CPUTimeoutMs` (default 10_000, TS
  #23812) stops guest JavaScript that runs longer than that in one invocation
  with `*codemode.CPUTimeoutError`. Time in host tools does not count. v0.5
  allowed pure JS to run up to the 30 s `TimeoutMs`.
- **Am I affected?** Long CPU-bound scripts.
- **What to do:** raise `CPUTimeoutMs` (and `TimeoutMs`) for long-running
  scripts.
- **Kind:** silent behavior change

### Code mode caps concurrent scripts {#codemode-max-workers}

- **What changed:** like TS, code mode runs at most floor(available memory /
  (`ExecutionPolicy.MemoryLimitBytes` + 48 MiB)) sandbox invocations at once,
  at least 1 and at most 32. v0.5 had no limit. A script started over the
  limit fails right away with `*codemode.ConcurrencyError` ("Code mode
  maxWorkers limit reached (N).").
- **Am I affected?** Servers that run many code mode scripts at once.
- **What to do:** raise the limit, or pass 0 to keep v0.5's unlimited
  behavior. `codemode.ResetMaxWorkers()` restores the default:

  ```go
  if err := codemode.SetMaxWorkers(64); err != nil {
  	log.Fatal(err)
  }
  ```

- **Kind:** silent behavior change

### wazero is v1.12.0 {#wazero-version}

- **What changed:** wazero moved from v1.9.0 to v1.12.0. Code mode's sandbox
  behaves the same: each invocation still gets its own QuickJS instance,
  memory and host bindings. QuickJS is now compiled once per process into one
  shared wazero runtime, so sandbox startup is faster.
- **Am I affected?** Modules that pin `github.com/tetratelabs/wazero`
  themselves.
- **What to do:** move your pin to v1.12.0.
- **Kind:** silent behavior change

## Harness, ACP and fx {#harness-acp-and-fx}

### ACP lifecycle state persisted by v0.5.x does not resume {#acp-state}

- **What changed:** as in TS (#23761), the persisted identity is
  `agentIdentity`, and the identity, configuration fingerprint and
  authentication digest are computed the TS way (including the client app
  version, so TS also rejects state after a package upgrade). Old state fails
  with "agentIdentity must be a string" or "ACP lifecycle state is
  incompatible with the configured ...".
- **Am I affected?** Saved ACP lifecycle state for the Cursor, GitHub Copilot,
  Grok Build and fx adapters.
- **What to do:** discard saved ACP lifecycle state and start fresh sessions
  after upgrading.
- **Kind:** silent behavior change

### A failed harness stop-condition suspension fails the turn {#harness-stop-suspend}

- **What changed:** when a `StopWhen` condition is met inside an `Agent` or
  `AgentSession` and the adapter's `DoSuspendTurn` returns an error
  (including `CapabilityUnsupportedError` from an adapter that cannot
  suspend), the turn fails with that error, as in TS. v0.5 finished the turn
  instead, so the error went unseen.
- **Am I affected?** `StopWhen` with an adapter that cannot suspend.
- **What to do:** handle the error from the turn, or leave out the stop
  condition.
- **Kind:** silent behavior change

### Harness adapters identify as ai-sdk-harness-id {#harness-client-app}

- **What changed:** harness adapters send `ai-sdk-harness-<id>/<version>` in
  `User-Agent` and `x-client-app`. The exported constants changed with them,
  for example `cursor.ClientAppName` is `ai-sdk-harness-cursor` (was
  `ai-sdk/harness-cursor`) and `cursor.ClientAppVersion` is a release
  version instead of `0.0.0-go`; the same holds for `fx`, `githubcopilot` and
  `grokbuild`.
- **Am I affected?** Server-side checks or tests that match the old values.
- **What to do:** match the new values, or read the constants.
- **Kind:** wire/protocol change

### With AgentSettings.Telemetry unset, the harness agent fires no telemetry {#harness-telemetry-unset}

- **What changed:** a harness agent without `AgentSettings.Telemetry` fires
  no telemetry, even to globally registered integrations.
- **Am I affected?** Harness agents that relied on global integrations.
- **What to do:** set `AgentSettings.Telemetry`.
- **Kind:** silent behavior change

### Harness usage is the turn total, and a failed OAuth refresh fails start {#harness-usage-oauth}

- **What changed:** `harness.Agent.Generate(...).Usage` is the turn total. For
  Claude Code and Codex, a failed OAuth refresh fails start instead of being
  treated as "no credential".
- **Am I affected?** Code that reads `Usage` as the last step's, or that
  expects start to fall back when a refresh fails.
- **What to do:** read per-step usage from the steps; handle the start error.
- **Kind:** silent behavior change

### fx: the built-in terminal tool is removed {#fx-terminal-removed}

- **What changed:** as in TS, fx has no built-in `terminal` tool.
  `inactiveTools: ["terminal"]` now returns an error.
- **Am I affected?** `"terminal"` in fx `BuiltinToolFiltering` lists or tool
  name checks.
- **What to do:** remove it from the lists.
- **Kind:** silent behavior change

### fx has an opt-in libfx runtime {#fx-libfx-opt-in}

- **What changed:** `fx.CreateFx()` without a `Runtime` behaves as in v0.5.x:
  the sandbox `fx acp` adapter, the v0.5.x `fx.BuiltinTools`, and v0.5.x
  lifecycle state. `fx.Settings{Runtime: fx.RuntimeLibfx}` selects the TS
  `@ai-sdk/harness-fx` runtime, which has other built-in tools
  (`fx.LibfxBuiltinTools`: `read`, `write`, `edit`, `bash`, `grep`, `glob`,
  `ls`, `askUserQuestions`). Its model requests leave from the host process.
  It authenticates with AI Gateway or, as in TS, a codex or grok subscription
  found on the host (`~/.fx`, `$CODEX_HOME` or the OS keyring, `$GROK_HOME`),
  and connects HTTP and SSE `MCPServers` from the host; command (stdio) MCP
  servers are not supported on it. The first session downloads the pinned
  `fx-core.wasm` (about 2.6 MB) into `os.UserCacheDir()/go-ai/fx/`. On a host
  without network access, pre-seed that cache or set `fx.WasmSource.Path`,
  then set `GO_AI_FX_OFFLINE=1`.
- **Am I affected?** Only if you set `Runtime: fx.RuntimeLibfx`. Sessions do
  not move between runtimes: a v0.5.x sandbox-ACP session resumed under
  `RuntimeLibfx`, or a libfx session resumed under the default runtime,
  returns `*fx.IncompatibleStateError`. As in TS, libfx state files are
  accepted for libfx 0.0.13 and 0.0.14; any other version, or a file that
  fails the schema, fails with "Cannot resume fx: the saved state is invalid
  or incompatible." An open turn suspended by a TS host cannot be continued by
  a Go host, or the other way round.
- **What to do:** no action unless you opt in. If you do, update
  `BuiltinToolFiltering` lists and tool-name checks, and finish or drop open
  sessions before you switch.
- **Kind:** silent behavior change

## Already changed in v0.5.3 {#already-in-v053}

These changes shipped in v0.5.3. They affect you only if you upgrade from
v0.5.0, v0.5.1 or v0.5.2. The [wrapper API key change](#wrapper-api-keys)
started in v0.5.3 too.

### Cohere uses the v2 API (v0.5.3) {#v053-cohere-v2}

- **What changed:** chat, embed and rerank use the v2 API under the base URL.
  `cohere.DefaultBaseURL` is `https://api.cohere.com/v2` (was
  `https://api.cohere.ai/v1`). A custom `BaseURL` without a version segment
  gets `/v2` appended; one ending in `/v1` or `/v2` is used as is. Embed sends
  `embedding_types: ["float"]`.
- **Am I affected?** A custom Cohere `BaseURL`, or a proxy that only forwards
  v1 paths.
- **What to do:** make sure the endpoint serves the v2 API.
- **Kind:** wire/protocol change

### Every provider retries (v0.5.3) {#v053-retries}

- **What changed:** `GenerateText`, `StreamText`, agents and `GenerateObject`
  retried only AI Gateway models. They now retry every provider (default 2
  retries), honor `ProviderError.Retryable` and retry connection failures.
  408, 409, 429 and 5xx are retried; 400 and 401 are not.
- **Am I affected?** Calls that must not be repeated, or your own retry loop
  around SDK calls.
- **What to do:** set `MaxRetries` to a pointer to 0 to disable SDK retries.
- **Kind:** silent behavior change

### The default HTTP client has no whole-request timeout (v0.5.3) {#v053-http-timeout}

- **What changed:** the default client had a 60 s whole-request timeout, which
  cut off long streams. It now has no whole-request timeout and a 5 minute
  response header timeout.
- **Am I affected?** Code that relied on the 60 s limit to bound calls.
- **What to do:** bound each call with its context:

  ```go
  ctx, cancel := context.WithTimeout(context.Background(), 60*time.Second)
  defer cancel()
  _ = ctx
  ```

- **Kind:** silent behavior change

### A call to an unknown tool does not stop the loop (v0.5.3) {#v053-unknown-tool}

- **What changed:** a call to an unknown tool is answered with a tool error and
  the `GenerateText` / `StreamText` loop continues. v0.5.2 stopped.
- **Am I affected?** Code that relied on the run stopping.
- **What to do:** no action unless you relied on the stop; use `StopWhen` or
  `RepairToolCall` to control it.
- **Kind:** silent behavior change

## Known differences from TS {#known-differences}

A few v0.6.0 behaviors differ from TypeScript on purpose. They are not
bugs. [Known differences from the TypeScript AI SDK](./known-differences.mdx)
lists all of them with the reasons. The ones you are most likely to notice
after upgrading:

- **`ToUIMessageStream` writes a masked `error` chunk** when its source stream
  fails, and ends the UI stream cleanly (owner decision 2026-10-29, the v0.5.x
  behavior). The SSE helpers then write `data: [DONE]` and close the response
  body without an error. TS errors the stream instead. See
  [UI message stream: source failure writes an error chunk](./known-differences.mdx).
- **The Vertex Gemini image model accepts URL and `gs://` input images**
  (owner ruling 2026-10-29). Current TS rejects them. Set `MediaType` for a
  URL without an image extension. See
  [Vertex Gemini image model: URL input images](./known-differences.mdx).
- **A `StreamText` tool context failure fails the run** (owner decision
  2026-10-28), as in `GenerateText` and the agents. TS streams an error part
  and finishes. See
  [StreamText tool context failure ends the run](./known-differences.mdx).
- **`WorkflowRunMultiplexer` does not require the `x-workflow-run-id`
  header.** It is a Go-only type with no TS twin. `WorkflowChatTransport`
  fails without the header, as TS. See
  [WorkflowRunMultiplexer run ID](./known-differences.mdx).
- **`codemode.SetMaxWorkers(0)` means unlimited**, kept from v0.5.x; TS
  rejects 0. See
  [Code-mode: never-settling promises and in-flight limits](./known-differences.mdx).
- **`StreamText` returns an invalid `Instructions` value synchronously**, and
  `WorkflowAgent.Stream` rejects a `MaxTokens` below 1. See
  [Option validation timing](./known-differences.mdx).
- **Each `WorkflowAgent` call has its own root call ID**; TS uses the literal
  `workflow-agent`. See [WorkflowAgent root call ID](./known-differences.mdx).
- **`InvalidArgumentError` text always starts with "Invalid argument for
  parameter ..."**, also where TS throws the provider package's
  `InvalidArgumentError`, whose message is the bare text. See
  [InvalidArgumentError message prefix](./known-differences.mdx).
- **Go does not check a model's specification version**, has no global
  default provider for a decision model ID, and the `Decide` telemetry
  events carry a subset of the TS fields. See
  [Decide: model version check and telemetry fields](./known-differences.mdx).
- **A `WorkflowAgent.Stream` run cancelled mid-stream ends its root span
  with `OnAbort`**, and the root telemetry `OnError`/`OnEnd` run after the
  user `OnError`/`OnEnd`. TS reports a thrown abort to the root `onError`,
  leaves the root open for an abort its iterator returns, and interleaves the
  user and telemetry callbacks. See
  [WorkflowAgent Stream: root telemetry at run end](./known-differences.mdx).
- **UI message stream SSE events have sorted JSON keys**, because
  `UIMessageChunk` is a map; TS writes insertion order. The values are the
  same. See [UI message stream JSON key order](./known-differences.mdx).
- **`ToUIMessageStream` frames a raw provider stream** (start, finish-step,
  finish, incomplete-stream error); start-led sources (`StreamText`, harness
  streams) map one to one as in TS. See
  [ToUIMessageStream on a raw provider stream](./known-differences.mdx).
- **The telemetry `OnStart` runs before the user `OnStart`**, so the
  callback runs in the integration's span context. TS starts the callback
  first; step-start and end events run the callbacks first, as TS. See
  [Telemetry start before the start callbacks](./known-differences.mdx).
- **`RuntimeContext` stays nil when unset**; TS defaults it to `{}`. See
  [RuntimeContext defaults to nil](./known-differences.mdx).
- **A failing parallel `EmbedMany` group returns after its other calls
  finish.** The error is the first failure in time, as TS, but TS rejects at
  once and lets the other calls run on. See
  [EmbedMany waits for sibling batch calls](./known-differences.mdx).
- **An aborted stream keeps the parts produced before the abort**; TS drops
  parts still queued in its stream pipeline. See
  [Abort keeps the parts produced before it](./known-differences.mdx).
- **Tool call input keeps keys the schema does not declare**; TS zod object
  schemas strip them. See
  [Tool call input keeps undeclared keys](./known-differences.mdx).
- **`Reasoning` lists hold reasoning text only**; reasoning file parts are
  returned by `StepResult.ReasoningFiles()`. See
  [Reasoning lists hold reasoning text only](./known-differences.mdx).
- **A tool output struct holding NaN or ±Inf becomes `null` as a whole**;
  typed maps, slices and arrays null only those numbers, as TS. See
  [Tool output structs holding NaN](./known-differences.mdx).
- **`WorkflowAgent.Stream`'s root span gets end attributes**; both TS OTel
  integrations throw while building them. See
  [WorkflowAgent root telemetry end](./known-differences.mdx).
- **`ConsumeStream` returns the stream's error**; TS `consumeStream()`
  swallows it. See [ConsumeStream returns the error](./known-differences.mdx).
- **Merged UI message streams interleave by goroutine scheduling**; each
  source keeps its order. See
  [Merged UI message stream order](./known-differences.mdx).
- **A provider tool error with no result value has the error text
  `tool error`**; TS leaves `errorText` undefined. See
  [Provider tool error without a value](./known-differences.mdx).
- **OpenAI provider tool args validation errors list the Go JSON Schema
  validator's issues** after "Error message:"; TS lists zod's issue JSON. See
  [OpenAI tool args issue text](./known-differences.mdx).

## For coding agents {#for-coding-agents}

Follow these steps in order. Do each step completely before you start the
next one.

1. Upgrade the module and tidy:

   ```bash
   go get github.com/digitallysavvy/go-ai@v0.6.0
   go mod tidy
   ```

2. Build and vet. Fix every error with the matching entry under
   [Compile-time changes](#compile-time-changes):

   ```bash
   go build ./... && go vet ./...
   ```

3. Search the code for each pattern in the
   [quick-scan table](#quick-scan-table). This command covers most of
   them; run it from the module root:

   ```bash
   grep -rnE --include='*.go' \
     -e 'MaxRetries:|RecordInputs:|RecordOutputs:|Evaluate(OnEnd|End)Event\{|EvaluationModelCallEndEvent\{|TextContentBlock\{"' \
     -e '\.Text\(\)|OnFinish:|TotalTokens|ReasoningText|OnError:|PrepareStep:|OnLanguageModelCallStart:|Request\(\)' \
     -e 'stream-start|response-metadata|FinishReasonOther|TimeoutError|PerStep|MaxTokens:|OnStartEvent|StopWhen:|"call-"' \
     -e 'AllowSystemMessages|InstructionMessages|ToolCallConcurrency|ToolChoice|ProviderExecuted|ToolResults|ContextSchema:|ToolApproval:' \
     -e 'ToolCallID|ActiveTools:|Request\.Messages|DeadlineExceeded|context\.Canceled|ResponseMessages|LanguageModelCallOptions|WorkflowStreamOptions' \
     -e 'workflowAgent\.generate|WorkflowRunMultiplexer|OnChatSendMessage|UIMessageStreamWithOptions|ToUIMessageStream|KeepAliveMs' \
     -e 'Integrations:|"ai-sdk"|"go-ai"|TracerName|EnrichSpan|onEvaluate|ai\.evaluat|err\.Error\(\)|\.Provider\(\)' \
     -e 'promptCacheOptions|OPENAI_API_KEY|DEEPSEEK_API_KEY|DownloadError|klingai|perplexity|Issuer|RequestTimeoutMS|TimeoutMS' \
     -e 'codemode\.|wazero|acp\.|ClientAppName|AgentSettings|"terminal"|fx\.Settings|policy\.|cohere' \
     -e 'OnStepStart|PrepareCall:|ParseCompleteOutput|StreamTranscri|no such (evaluation|decision)Model|finishReason|is not allowed' \
     -e 'ToUIMessageChunk|event\.Ranking|ToolErrorContent|IsError|RepairText|NewStreamTextResultFromParts|xai\.(MCPServer|FileSearch)' \
     -e 'ai\.ranking|SerializableToolDef|ToolApprovalResponseContent|ConsumeSSEStream|NoObjectGeneratedError|ProviderMetadata|ReasoningFile' \
     -e 'openaitool\.|anthropic/tools|gateway/tools|providers/xai|\.Title|tool_search|NewShellTool|ProviderArgs|Warnings' .
   ```

4. For each match, open the entry the table links to. Apply **What to do**.
   If the entry says "No action unless you ...", check the condition and
   move on if it does not apply.
5. Check what the grep cannot find: telemetry dashboards and queries
   ([Telemetry and events](#telemetry-and-events)), persisted ACP or fx
   state ([ACP state](#acp-state)), environment variables for wrapper
   providers ([Wrapper API keys](#wrapper-api-keys)), OpenAI-compatible
   servers that reject `tool_choice` ([Unset ToolChoice](#tool-choice-auto)),
   and golden files with escaped JSON ([JSON escaping](#json-not-html-escaped)).
6. Run the tests with the race detector, since tools now run concurrently:

   ```bash
   go test -race ./...
   ```

7. Fix failing tests by the entry that covers them. Do not change an
   assertion to match new behavior unless an entry on this page describes
   that behavior.
