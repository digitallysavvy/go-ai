# Known differences from the TypeScript AI SDK

The Go AI SDK tracks the TypeScript AI SDK (`ai@7.0.153` as of v0.6.0) closely, but a
few areas are intentionally different, either because the Go runtime has no
equivalent primitive or because a decision was made to diverge. This page is
the reference for both.

## StreamObject is not lazy

`StreamObject` is deprecated in both SDKs. In TypeScript, `streamObject`
returns lazy streams immediately, before the model call completes. In Go,
`StreamObject` returns only after the stream is fully consumed, and reports
progress through `OnChunk` as the partial object is refined.

For incremental partial objects or array elements, use `StreamText` with
`Output` (`PartialOutput` / `ElementStream`) instead — this is also what the
TypeScript SDK recommends going forward.

```go
// Not recommended: StreamObject blocks until the stream finishes.
result, err := ai.StreamObject(ctx, ai.StreamObjectOptions{
    Model:  model,
    Prompt: "Generate a recipe",
    Schema: recipeSchema,
    OnChunk: func(partial interface{}) {
        // Called incrementally as the partial object is refined.
    },
})

// Recommended: StreamText + Output returns immediately and lets you read
// the incrementally parsed value as chunks arrive, matching TS's lazy
// streamObject.
textResult, err := ai.StreamText(ctx, ai.StreamTextOptions{
    Model:  model,
    Prompt: "Generate a recipe",
    Output: ai.ObjectOutput[Recipe](ai.ObjectOutputOptions{Schema: recipeSchema}),
})
for chunk := range textResult.Chunks() {
    if chunk.Type == provider.ChunkTypeText {
        partial := textResult.PartialOutput() // latest parsed partial value
        _ = partial
    }
}
```

When the stream itself fails (`Next()` returns an error, rather than the
provider sending an error part), Go still calls `OnStepEnd` and `OnEnd` with
the error and ends the call's telemetry. TypeScript never runs its flush
handler in that case, so it calls neither and leaves the root span open.

When the stream ends cleanly without a finish part, Go still parses and
validates the accumulated text and returns the object (finish reason
`other`). TypeScript only parses the object in its finish handler, so there
it calls `onFinish` with no object and no error, and `result.object` never
settles.

## Video generation webhook suspension in workflows

TypeScript's `experimental_generateVideo` can durably suspend a Vercel
Workflow DevKit run until a provider webhook fires, resuming the workflow
from durable storage when the video finishes. This depends on the Node-only
Workflow DevKit runtime and has no Go equivalent.

In Go, video generation polls until the job is done (`GenerateVideo`), or you
drive the job yourself with `ai.ExperimentalStartVideo` /
`ai.ExperimentalGetVideoStatus`, which support both polling and webhook
completion (fal and Replicate) outside of a workflow.

## Vercel Sandbox: no OIDC token refresh loop

`pkg/harness/sandbox/vercel` (the Go port of `@vercel/sandbox`'s harness
provider) does not run a background `@vercel/oidc` token refresh loop.
`VERCEL_OIDC_TOKEN` is re-read from the environment on each call instead;
explicit `Token` / `TeamID` / `ProjectID` credentials also work and bypass
OIDC entirely.

## Code-mode: never-settling promises and in-flight limits

`pkg/codemode` runs model-written JavaScript in a QuickJS-on-WebAssembly
sandbox (wazero). Concurrent tool calls that need approval (for example
inside one `Promise.all`) are batched into a single interrupt, as in TS.
These details differ:

- A promise that never settles and has no pending tool call fails fast
  with a `ProtocolError`. TypeScript waits for the execution timeout.
- `MaxInFlightBridgeRequests` counts the calls in an approval batch.
- `SetMaxWorkers(0)` means no concurrency limit; TypeScript rejects 0.
- On platforms other than Linux, macOS and Windows, the default worker cap
  is 32, because Go cannot read available memory there without cgo.
- A resumed run whose `ToolExecutionOptions` has an empty `ToolCallID`
  keeps the continuation's outer tool call ID. Go cannot tell an empty ID
  from an unset one; TypeScript keeps an explicit `""`.

## MCP transports

- Transport failures that wrap a Go error (a failed dial, a broken pipe, a
  request sent before `Connect` on `HTTPTransport`) are `*TransportError`,
  whose text starts with `transport error: `. TypeScript lets the runtime's
  own error through, and its text differs from Go's anyway. Errors that TS
  creates itself use the TS text.
- `HTTPTransport` reports a failed POST (an HTTP error status, an
  unexpected content type, a failed authorization) to `OnError` once.
  TypeScript reports these twice, because its inner and outer `catch`
  blocks both call `onerror` with the same error.
- `SSETransport.Connect` interrupted by `Close` before the endpoint event
  returns an error. TypeScript's `start()` never settles once it is aborted.
  `HTTPTransport.Connect` interrupted by `Close` (for example while it
  refreshes an OAuth token) also returns an error and leaves the transport
  closed; TypeScript's `start()` cannot be interrupted.
- `Connect` after `Close` starts the transport again, as in v0.5.
  TypeScript's HTTP transport fails with "Transport already started", and
  its stdio transport never finishes starting.
- After a stdio server process exits on its own, `StdioTransport.Send`
  fails with a `*TransportError` for the closed pipe. TypeScript clears the
  process on its `close` event and throws "StdioClientTransport not
  connected". Go learns of the exit only through `Close`, which waits on
  the process.
- After a read error on its stream (once the endpoint event has arrived),
  `SSETransport` marks itself disconnected: `Send` fails with "Not
  connected" and `Receive` returns the stream error. TypeScript only reports
  the error through `onerror` and stays connected, so a later send still
  POSTs, but its reply can never arrive over the dead stream. Go fails fast
  instead, as in v0.5.
- `HTTPTransport.Close` waits for its background goroutines (inbound SSE,
  reconnect timers, readers of event-stream POST responses), except one
  that is inside an `OnError`, `OnSessionIDChange` or `OnSessionExpired`
  callback, so that the callback can call `Close`. That goroutine exits
  once its callback returns. It also does not wait for an OAuth
  authorization the inbound SSE GET started after a 401: as in TypeScript,
  `Close` does not cancel that flow, and its failure is still reported to
  `OnError`.

## fx: libfx runtime

- **Opt-in, not the default.** TS `createFx()` always runs libfx. Go keeps
  the v0.5.x sandbox `fx acp` adapter as the default (`fx.RuntimeSandboxACP`)
  and runs libfx with `fx.Settings{Runtime: fx.RuntimeLibfx}`. Making libfx
  the default would change the built-in tools, the network path and the
  lifecycle state for v0.5.x callers.
- **wasm only.** Go runs libfx's `fx-core.wasm` on wazero. The Node native
  addon (`backend: "native"`) is not available.
- **The credential stays on the host.** The TS host puts the AI Gateway key
  in the core's environment. Go gives the core a placeholder and swaps in
  the real key on the host, only for AI Gateway requests, and removes the
  key from responses.
- **Origin allowlist.** The core's requests, and the redirects they follow,
  may reach only the AI Gateway base URL and libfx's provider origins; TS's
  fetch allows any URL. A Gateway request path that is itself a URL stays a
  path on the base URL, where TS's `new URL(path, base)` would resolve it to
  that other origin.
- **Asynchronous tool-result echo.** Turn parts reach `Emit` from one
  goroutine per turn. TS emits the echo of `submitToolResult` before its
  promise resolves; Go's `SubmitToolResult` returns once the result is saved,
  and the echo follows on `Emit`.
- **Subscription hardening.** Like libfx, Go masks the subscription tokens a
  failed response repeats in its body; it also masks them in response
  headers of any status, masks both the rejected and the refreshed tokens
  after a `401` retry, adds credentials only to the selected provider's
  endpoints (libfx would also authorize Grok endpoints on a codex agent and
  the reverse), bounds OAuth token responses at 1 MiB, and refuses a
  redirect that would carry the credentials to another origin. Of `https://x.ai`
  the core may reach only `https://x.ai/cli/stable`, where the grok provider
  reads the Grok CLI version without credentials.
- **MCP server order.** Go maps have no insertion order, so `MCPServers` are
  connected, and their tools listed, in server-name order unless
  `Settings.MCPServerOrder` gives the TS object's key order. Structured MCP
  tool output is serialized with sorted object keys.
- **Edge cases only the core or a crafted request reaches.**
  - The Gateway transport's model-request check uses Go's decoded URL path,
    where TS uses the WHATWG `pathname` (percent-encoded, dot segments
    removed).
  - The Responses endpoint check ignores the URL's userinfo and fragment,
    which TS `href.split('?')[0]` keeps.
  - A host tool image with `data: ""` and no `sourceRef` is rejected as an
    invalid tool image; TS keeps it. Go's `ToolImage` cannot tell an empty
    string from an absent one.
  - The `toolStartInput` size limit measures the raw wire bytes, where TS
    measures `JSON.stringify(rawInput)`. They differ only near the 64 KiB
    limit.
  - `realpath` decodes the sandbox's base64 output strictly (standard
    alphabet, padding required); Node's `Buffer.from(..., 'base64')` skips
    characters outside the alphabet. Invalid UTF-8 in the decoded path
    becomes U+FFFD in both. The `base64` command's own output decodes the
    same way in both.
  - When a `bash` `timeout` passes, the error text is what the sandbox
    returns for a cancelled context (usually `context deadline exceeded`);
    TS gets the sandbox's rejection for a `TimeoutError` ("The operation was
    aborted due to timeout").
  - The `glob` tool does not support minimatch extglobs (`@(a|b)`,
    `!(a)`, `+(a)`, `*(a)`, `?(a)`); their characters match literally.
  - Where Node's `path.matchesGlob` throws "Invalid regular expression ...
    Invalid escape" (a segment with a Unicode posix class such as
    `[[:alpha:]]` next to a literal `-`, `,`, `#` or space), Go matches the
    segment instead of failing the tool.
  - Brace patterns cost about what they cost in Node: minimatch's
    second-phase merge is quadratic in the number of expansions, so
    `{a,b}` repeated 17 times takes tens of seconds of CPU in both. Node
    cannot interrupt the synchronous compile; Go stops it when the tool
    call's context ends and the tool fails with the context's error.
    Braces nested thousands of levels deep make Node throw "Maximum call
    stack size exceeded"; Go expands them, slowly, until the context ends.

## Harness file reporter

- A step's `output` is rebuilt from the step-end telemetry event (text,
  reasoning, files, tool calls, tool results), so it omits the approval
  requests and sources that TS `step.content` holds, and writes
  `"input": null` where TS leaves an undefined input out.
- When a provider-executed tool sends a preliminary result and then its
  final result, TS pushes the first `toolOutput` into the model-call content
  twice; Go records each result once.

## Google batch and Perplexity: empty values and fractional counts

- **Google batch cursor and webhook.** `BatchV4ListOptions.Cursor` and
  `BatchV4StartOptions.WebhookURL` are strings, so an empty value is the same
  as unset. TS sends `pageToken=` for `cursor: ""` and a `webhookConfig` for
  `webhookUrl: ""`; Go sends neither. A response `nextPageToken: ""` is
  reported as no `NextCursor`, where TS returns `nextCursor: ""`. An empty
  `metadata.state` and `responsesFile` are kept as values, like TS, but
  `BatchV4Status.RawStatus` cannot tell `""` from absent.
- **Perplexity fractional counts.** TS `z.number()` accepts counts such as
  `12.5`. Go accepts them too and truncates usage counts toward zero, because
  `types.Usage` holds integers. `providerMetadata.perplexity.usage` and
  `toolCalls` invocation counts are truncated the same way.

## Gemini and Perplexity streaming

- **`[DONE]` marker.** Gemini and Perplexity streams stop reading at a `[DONE]`
  SSE marker. TS `parseJsonEventStream` skips the marker and keeps reading, so
  events after it reach TS callers but not Go callers.
- **Accept header.** Streaming requests send `Accept: text/event-stream`, an
  SDK-wide Go convention. TS sends no `Accept` header.
- **Google usage metadata merge.** When a long-decode response spans several
  requests, the summed `usageMetadata` keeps the earlier `serviceTier` and
  `trafficType` if a later request sends an explicit `null`. TS merges with
  `{...a, ...b}`, so the `null` overrides the earlier value.

## WorkflowAgent root call ID

TS gives every `WorkflowAgent` root (and its `executeTool` events) the
literal call ID `'workflow-agent'`. Go gives each `Generate` or `Stream`
call its own ID. A constant ID would collide in an integration's call-state
map when two runs share an integration concurrently, and would break
correlating events with their run.

## Option validation timing

- `StreamText` returns an invalid `Instructions` value (a non-system
  message) as its error, synchronously. TS `streamText` validates the prompt
  inside its async run, so the error arrives as an error part or a rejected
  promise, after the `maxRetries` check. Go reports it the way its other
  `StreamText` validation errors are reported, as v0.5.x did.
- `WorkflowAgent.Stream` rejects a `MaxTokens` below 1 before the model call
  (`InvalidArgumentError` "maxOutputTokens must be >= 1"), as
  `WorkflowAgent.Generate` and TS `generateText` do. The TS WorkflowAgent
  stream path (`doStreamStep`) does not check it and sends the value to the
  provider.

## StreamText tool context failure ends the run

When a tool's `ContextSchema` rejects its tool context, TS
`executeToolsFromStream` catches the throw and enqueues an `error` part. The
TS stream goes on: the step finishes with no tool output, so the run ends
with `finish` and `onEnd`. Go ends the run with the `ValidationError`: the
stream stops with no `finish-step` or `finish`, `OnEnd` is not called, and
`Err()` returns the error. `OnError` is called once, as TS calls `onError`
for the error part. This keeps StreamText in line with `GenerateText` and the
agents, where a tool context failure fails the call (owner decision,
2026-10-28).

## JSON payloads with `__proto__`

Go accepts JSON with a `__proto__` key or a `constructor.prototype` member
in provider responses and stream chunks. TS `secureJsonParse` rejects those
payloads (a `JSONParseError`) as a guard against JavaScript prototype
pollution. Go `encoding/json` decodes into maps and structs, which have no
prototypes, so there is nothing to guard against, and rejecting the
payloads would only turn valid JSON into errors.

This difference covers provider responses and stream chunks only. Prompt
conversion follows TS: a stringified Google Interactions tool-call input with
such a key is sent as `{value: input}`, as TS `safeParseToolArgs` does when
`secureJsonParse` throws.

The Gemini prompt converter (`generateContent`, Google and Vertex) accepts a
string tool-call input with such a key for `code_execution` and server tool
calls, where TS `secureJsonParse` throws. In Go, `ToolCallContent.Input` is
always the wire text, also for inputs that TS holds as objects and passes
through without parsing, so throwing would reject inputs that TS accepts.

## Empty strings in provider response fields

- **Typed string fields.** Some exported response structs hold a value as a
  plain `string`, so `""` reads the same as an absent field: Gemini
  `finishMessage`, `usageMetadata.serviceTier` and `continuationToken`;
  Google interactions `signature`/`thought_signature`, the completed
  `service_tier` and a file `mime_type`; Anthropic and Bedrock
  `stop_sequence`. TS checks `!= null`, so `""` counts as present there.
  Changing these fields' types would break v0.5.x callers, and the real APIs
  do not send these empty values. An interactions builtin-tool
  `delta.result: null` is not stored; TS stores `null`.
- **Interactions id on `interaction.created`.** An `interaction.created`
  event with an empty id keeps the interaction id from an earlier event. TS
  resets it, but Go also uses that id to reconnect to and cancel the
  interaction.

## Google Interactions tool call IDs

A non-streaming Interactions response whose `function_call` step has no
`id` (or an empty one) gets an ID from the provider's ID generator
(`Config.GenerateID` or `InteractionsConfig.GenerateID`, else a random ID),
as other Go providers do for missing tool call IDs. TS keeps the empty or missing ID. Go matches
tool results and approvals by ID, so an empty ID, or the per-response
`call_N` counter v0.5.2 used, could repeat across the steps of one run.

The stream fallback follows TS: a step without an `id` is named
`<interactionId>:<index>`, and `interaction:<index>` when the response has
no interaction id (`store: false`). Under `store: false` that fallback can
repeat across steps.

## Features that are TypeScript-only (not ported)

- **OpenAI Live over WebRTC** — the browser transport for OpenAI's realtime
  API. The Go SDK only implements the server-side WebSocket transport
  (`gpt-live-1` via `ai.ConnectRealtime`), which covers server-side and
  backend use cases; WebRTC is a browser-only transport with no Go runtime
  equivalent.
- **`@ai-sdk/harness-cline` and `@ai-sdk/harness-pi`** — these harness
  adapters run vendor Node SDKs in-process (they embed a Node.js runtime and
  the vendor's own TypeScript SDK). There is no Go equivalent; use the
  TypeScript SDK for Cline or Pi harness integrations.
- **DeepSeek batch API / extra Files methods** — TS's `@ai-sdk/deepseek` does
  not implement these either, so this is parity, not a gap; the existing
  DeepSeek file support already matches TS.

## Streaming pattern: Next() instead of io.Reader

This is a longstanding, deliberate Go-idiom difference (not new in v0.5.0):
`provider.TextStream` exposes `Next()` / `Err()` / `Close()`, not an
`io.Reader`. See the [Streaming guide](../guides/STREAMING.md) for the
rationale.
